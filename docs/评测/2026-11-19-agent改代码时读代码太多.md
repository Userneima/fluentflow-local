# agent 改这个仓库时，时间花在读代码上：原因和改法

2026-11-19，按 product-lens 评。触发：王愉超发现别的对话改这个项目时大量时间花在读代码上，问是不是代码哪里做得不行。

## 对象和用户

- 对象：这个仓库本身（代码 + 给 agent 的入口文档）。
- 主要用户：来改它的 agent。它要完成的事：接到一个改动，尽快找到该改的地方和相关的已定规矩，改对，再把受影响的文档同步。
- 次要用户：王愉超（他不读代码，只关心改得快不快、对不对、花多少额度）。
- 阶段：用久了开始臃肿。一个月内 2318 次文件改动，靠一次次补丁长大。比重最高的是范围、内容、成本。

读操作本身耗时很短（每个对话合计不到 1 到 20 分钟）；代价在读进来的内容占满上下文，模型要在里面找、想，对话也更早被压缩。所以「读的输出占比」是拿来代替「花在读上的时间」的数。

读得最多的文件（一个对话里同一文件被读的次数）：

- `docs/02-决策记录.md`：每个对话 6 到 25 次。2408 行、约 36 万字节（估计 10 万 token 以上，没法一次读完，只能反复 grep、分段读）。也是一个月里改得最多的文件（179 次提交）。`AGENTS.md` 要求改动前查对应部分、改完写一条，且不许删条目，只许追加。最大的一节「六、产出文件与任务状态」有 860 行。
- `frontend/src/routes/editor.jsx`：2414 行，其中 `Editor` 一个组件从 297 行写到 2411 行，约 2100 行在一个函数里。转录稿跟随那个对话读了它 38 次。
- `frontend/src/routes/agent-tasks.jsx`：1346 行，一个对话读了 44 次。
- 后端大文件：`video_source.py` 2743 行（115 个函数）、`silence_cuts.py` 2361 行、`scripts/fluentflow_mcp_server.py` 2359 行、`local_agent.py` 1889 行、`media_job.py` 1816 行。
- 每次改动要同步的文档有 7 份（待办、决策记录、更新记录、README、AGENT_INSTALL、agent 的 SKILL、MCP 工具说明、维护手册），`AGENTS.md` 要求推送前逐份搜一遍，这些也算在「读」里。

做得好的部分：后端 157 个模块里 155 个开头有说明；`AGENTS.md`「Where things are decided」给每个概念指定了唯一的文件，并有测试守着。后端找文件不难，难在找到之后文件太长。

## 判断

代码确实有问题，但不是全部问题。读的量里排前面的两样：

1. **决策记录太大，又是每次必读必写**。它只追加不删，被取代的旧结论还留在原处，agent 要读完一串条目才知道现在哪条算数。这是最大的一块。
2. **前端两个页面是巨型文件**，尤其编辑页一个组件两千多行，改一个小交互也得一段段读上下文。后端几个两千多行的文件同理，程度轻一些。

此外，「改完同步 7 份文档」的规矩本身合理，但让每个对话的读量再多一截。

## 证据缺的

- 用户的反应：只有王愉超这一句观察，没有每次对话的耗时记录。补法：拆完后重跑本页的统计脚本做前后对比。
- 外面的标杆：两条出处都是凭已有知识，未核原文。
- 亲眼看一次：没有。下一次改编辑页的对话就是一次观察机会。
- 只有自评，没开独立评审：对象是测量结果明确的诊断，结论靠数据而不是判断。
