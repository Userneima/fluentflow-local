## 1. MLA、MTP、混合注意力、KV cache

### 旧版

**（二）混合注意力 vs MLA**

- 团队选了 **Hybrid Attention（混合注意力）**：把全注意力层（full attention，每个 token 看全部上文）和滑动窗口注意力层（sliding window attention，每个 token 只看最近一段窗口）按比例混合。
- 当时更主流的选择是 **MLA**（DeepSeek 提出的注意力结构，通过压缩大幅减少 KV Cache）。同期开始训练的 GOM（存疑）和 Kimi 都选了 MLA。
- **KV Cache**：推理时为每个已生成 token 缓存的注意力键值，长上下文时占显存很大，所以很宝贵。
- 嘉宾的评价：MLA 对聊天（Chat）时代是非常优秀的结构，对长文也还不错，因为它大量减少了 KV Cache。

**（三）MLA 为什么不太适合 Agent：没有加速余地**

- MLA 是为了在当时的 H 系列芯片上达到很好的访存与计算比例而设计的：既不浪费算力，又打破访存瓶颈。
- 推理时有两种瓶颈：**计算受限**（compute bound，算力先用满）和**访存受限**（memory bound，显存读写带宽先用满）。MLA 正好卡在两者的完美临界点上，因此**没有可发挥的空间**。
- 「可发挥的空间」指：如果认为 KV Cache 和推理速度都重要，能不能用加速手段，比如最简单的投机解码（speculative decoding，先快速猜出后面几个 token，再由主模型一次性验证）。**MTP**（multi-token prediction，多 token 预测，模型一次预测后面多个 token）就是一种方式，可以让实际推理加速很多倍。
- 但 MLA 上了 MTP 后又会卡在计算瓶颈上，很不划算。所以她猜测 GOM（存疑）、Kimi 这些 MLA 结构的模型都没有上 MTP，模型会慢一些。

### 新版

**（二）混合注意力和 MLA 的取舍**

下面几个概念都围绕同一个问题：模型生成每个新词时都要回看前面的内容，内容越长越占显卡内存、越慢。

- **KV cache**：为了不重复计算，模型把前文算好的中间结果存在显卡内存里，这份存档就是 KV cache。上下文越长，它越大。
- **访存瓶颈和计算瓶颈**：前者指速度卡在从内存搬数据上，后者指速度卡在显卡算力上。理想状态是两者正好平衡，哪边都不浪费。
- **MLA**：DeepSeek 提出的一种注意力结构，把 KV cache 压缩得很小。
- **混合注意力（hybrid attention）**：小米的选择。模型里少数层是**全注意力层**（full attention，每次回看全部前文），多数层是**滑动窗口层**（sliding window attention，只回看最近一段）。滑动窗口层存的东西少，所以省 KV cache。
- **MTP 和投机解码**：MTP（multi-token prediction，多 token 预测）让模型一次多预测后面几个 token。token 是模型处理文字的最小单位，大致是一个字或一个词片段。投机解码（speculative decoding）指先快速猜出后面几个 token，再由主模型一次性核对，猜对的直接收下，这样一步能出好几个 token。

当时更主流的选择是 MLA。嘉宾说同期开始训练的 GLM-5 和 Kimi 都选了 MLA，Kimi 更早，K2也更早。她认为 MLA 在聊天（Chat）时代是非常优秀的结构，对长文也还不错，因为它大量减少了 KV cache。但她认为 MLA 有不太适合 Agent 范式的根本问题：

- MLA 设计之初，就是为了在当时的 H 系列芯片上，把访存和计算调到正好平衡，「既不浪费算力，又打破访存瓶颈」。
- 这样设计出来的结构没有可发挥的空间。如果还想用投机解码、MTP 让推理再快 N 倍，MLA 又会卡到计算瓶颈上，很不划算。
- 所以她**猜测**，用 MLA 的模型（GMO（存疑）也好、Kimi 也好）应该都没有在推理时上 MTP，模型也就会慢一些。

### 第二版

**二、为什么没选更主流的 MLA**

下面几个词说的都是模型生成文字时的速度和成本：

- **KV Cache**：模型生成每个新字时要回头看前文，KV Cache 是把前文算过的中间结果存起来，避免重算。上下文越长，它占的显存越多。
- **访存和计算**：模型推理时一部分时间花在从显存里搬数据（访存），一部分花在算数（计算）。卡在搬数据上叫 Memory Bound（瓶颈在访存），卡在算数上叫 Compute Bound（瓶颈在计算）。两者都不浪费，硬件才用得最充分。
- **MTP**（Multi-Token Prediction，让模型一次预测好几个字）：投机解码（先快速猜出几个字，再一次性检验）的一种做法，能让推理加速好几倍，代价是要多做计算。

当时更主流的选择是 DeepSeek 提出的 MLA（Multi-head Latent Attention，一种把 KV Cache 压缩得很小的注意力结构）。和他们同期开始训练的 GOM（存疑，后文又作 GMO）、Kimi 都选了 MLA，罗福莉说 Kimi 更早一些，又说「KAR（存疑）更早一些」。

她对 MLA 的评价：

- 在 Chat（单轮或多轮对话）时代，它确实是非常优秀的结构；对长文也算不错，因为它大量减少了 KV Cache，而长文场景下 KV Cache 很宝贵。
- 但它有几个根本性的点，让它不太适合 Agent（能自己调用工具、连续执行多步任务的模型应用）。

**MLA 没有给加速留空间**：MLA 当初的设计目标，是在当时的 H 系列芯片（英伟达 H100 这一代 GPU）上把访存和计算的比例调到最好，既不浪费算力，又打破访存瓶颈。结果它正好卡在 LBound（存疑，按上下文应指计算瓶颈）和 Memory Bound 的临界点上。如果你认为 KV Cache 重要、推理速度也重要，想再用 MTP 这类方式加速，MLA 就不太行：加上 MTP 后又会卡在计算瓶颈上，很不划算。

她**猜测**用 MLA 结构的模型，不管是 GMO（存疑）还是 Kimi，应该都没有上 MTP，所以它们的模型会慢一些。

**三、Hybrid Attention 加 MTP：省 KV Cache，又把省下的算力用来提速**

这套结构的做法分两步：

1. **用滑动窗口层省 KV Cache**：模型里有两种层，Full Attention 层（每次看完整前文）和 Sliding Window 层（每次只看最近一段文字，所以 KV Cache 小、计算也少）。在 Pro 这一代，他们把两者的比例拉得更极致，达到 7 比 1，因此更省 KV Cache，能支持更长的上下文。
2. **用 MTP 填上省下的算力**：Sliding Window Attention 省下来的那部分计算，用 MTP 填满，让实际推理时访存和计算达到很好的平衡，同时兼顾长上下文的成本和推理速度。

罗福莉说，这是这种结构，尤其是针对「Non-Colus Inflation（存疑）」的结构带来的优势。速度上的数字：

- 第一代 Flash 能做到每秒 100 到 150 TPS（每秒生成的 token 数，token 是模型处理文字的最小单位）。
- Pro 基本能做到 60 到 100 TPS，具体看成本，100 TPS 肯定更贵一些。

所以用户用 Memo（存疑）的 Flash 或 Pro，感觉都是「好快」，同时成本足够低。

**模型变强后还要精巧编排吗**：还需要，出于成本考虑。生产力革命的基本要求，是永远追求成本最低、效率最高的方案，不可能所有场景都用最贵的顶尖模型。更可能的是 agent 在进化、模型在进化。模型的一种进化方式是同一水平的模型越变越小（团队没在做这个，但确实是一种方式）。她认为「大概率会发生」的是：现在激活 10B 的模型，一年后可能就能做到 Claude Opus 4.6 的水平。激活参数指模型每次回答实际动用的那部分参数，越少越便宜越快。这种模型很便宜，可能一两块钱就能用上百万 token 的上下文，反应更快，基于这套框架很好用，还能改框架，为什么不用？

（……中间略……）

- 被问到参数量能不能决定智力上限，她说现在认为是**参数量加上下文共同决定**。要让大家觉得接近 Opus 4.6 这一代最强 Agent 的水平，她自己认为至少要总参数 1T 以上，但也说不知道 Opus 4.6 本身有多大。

### 第二版

**更可能的走向**：Agent（能自己分步骤调用工具、完成任务的 AI 程序）在进化，模型也在进化。模型进化的一种方式是：同一个水平的模型越变越小。她特意说明她们自己没有在做这件事，但这确实是一种进化方式。
- 例子：现在激活 10B 的模型（每次回答实际参与计算的参数约 100 亿个；参数越少越便宜），可能过一年就能做到 Claude Opus 4.6 的水平。她认为这件事大概率会发生。
- 激活 10B 的模型很便宜，可能一两块钱就能用到百万量级的上下文（模型一次能读进去的文字量）。
- 所以为什么不用更小的模型：反应速度更快、更迷米（存疑）；基于这套一件框架（存疑）很好用，还可以改这套框架，没有理由不拥抱它。

（……中间略……）

**一、参数量与智力上限：至少 1T 总参，激活参数更关键**

小俊问：参数量能不能决定模型智力的上限，是不是模型越大越好。

罗福莉说她现在的看法是：参数量和 context（上下文，模型一次能读进去的内容长度）**共同决定**智力上限。

- **门槛**：要让大家觉得已经很接近当下公认最强的 Agent（智能体，能自己分步骤调用工具完成任务的模型）水平，比如接近 4.6OPS（存疑）那样的水平，她认为总参数至少要 1T（一万亿个参数）以上。她特意说明，她不知道那个模型实际多大，这只是她个人的判断。
- **激活参数更关键**：总参数（模型里全部参数的数量）之外，更关键的是激活参数（每次处理一个词时实际参与计算的那部分参数）。比如总参同样是仪体（存疑），激活参数越大，推理成本（模型每回答一次要花的算力和钱）越高。所以激活参数要大到多少是一个 trade-off（取舍：多得一样就要少得另一样）。

### 旧版

**（三）Omni：仍是连续表征的 ViT**

- 主持人以为 Omni 构建了统一的表征。嘉宾说没有：Omni 的视觉编码器还是 ViT（Vision Transformer），只是变成了更高效的 hybrid sliding window ViT，表征本身仍是连续的。

### 新版

主持人以为 Omni 是在构建统一的多模态表示，嘉宾说没有。Omni 的视觉部分还是 ViT（处理图片的常用模型结构），只是改得更高效，变成了混合滑动窗口的 ViT；表示本身还是连续的，没做太多变化。

### 第二版

**二、Omni 没有改表征方式，"全模态"指它支持所有模态并能同时理解音视频**

下面几个词都和模型怎么"看"图像有关：ViT（Vision Transformer，把图片切成小块再交给模型处理的视觉编码器）；Sliding Window（滑动窗口，每一块只和附近的块计算关系，以减少计算量）；Hybrid（混合，这里指把滑动窗口和其他计算方式搭在一起用）；连续表征（用一串连续的数值描述图像内容，和把图像转成一个个离散符号的做法相对）。

小俊问：Omni 是不是走了另一条路，不是先分别处理各个模态（文字、图片、音频、视频这类不同类型的输入）再拼到一起，而是试图构建一个统一的表征？

罗福莉说不是。Omni 的 ViT 还是 ViT，只是改得更高效了，变成了 Hybrid Sliding Window 的 ViT；表征本身没有做太多变化，仍然是连续表征。

接着说到为什么叫"全模态"而不是"多模态"：
- Omni 确实支持视频、音频、图片、文本所有模态；
- 有一些 Agentic 模型（能自己规划步骤、调用工具完成任务的模型）不支持音视频的联合理解（同时理解一段视频里的画面和声音）；
- 罗福莉说 Omni 应该是第一个既支持音视频联合理解、Agentic 能力又能做到和 Language Model（只处理文字的语言模型）水平差不多的模型。

## 4. RL Infra、推理引擎

### 旧版

**二十八、模型结构要提前规划，RL Infra 要跟着 Agent 重做**

**预训练和 Infra 要前置**：嘉宾认为，这一代模型结构到底为什么准备（一种「战略定性」），要提前想清楚。以前她觉得要提前一年，现在觉得半年，因为 Agent（智能体，能自己调用工具、多步完成任务的系统）会让节奏加快。想不清楚的话，模型结构就是平庸的。她特别区分了两点：平庸的结构**不一定**带来平庸的效果，但一定会带来**成本和效率上的劣势**。所以预训练和 Infra（基础设施，这里指训练、推理用的软件系统）要提前做很多事。

**后训练没法前置规划**：后训练（预训练之后用强化学习等方法继续训练）现在是和 Agent 耦合在一起迭代的，很多事提前规划不清楚。更考验的是团队怎么根据当下的模型能力和 Agent 范式产生的「化学反应」，快速设计新的 RL Infra（强化学习训练系统）。

**两代 RL Infra 的区别**：

| | Code / Math 推理（Reasoning）时代 | Agent 时代 |
|---|---|---|
| 核心 | 模型的推理引擎本身，因为模型要想很久再给答案 | 不只是推理引擎，还要处理模型和 Agent 框架的耦合 |

### 新版

**三十、模型结构要提前想清楚，后训练和 RL Infra 要跟得快**

嘉宾（说话人 B）认为，训练一代模型之前，要先定下这一代模型「是为什么准备的」。以前她觉得要提前一年想，现在觉得提前半年，因为 Agent 让一切变快了。没想清楚的话，模型结构就会很平庸。平庸的结构**不一定带来平庸的效果**，但**一定带来成本和效率上的劣势**。

先交代这一节几个词的关系。做一个大模型分两大阶段：预训练（用海量文本先把模型的基本能力练出来）和后训练（在练好的模型上再针对具体用途加练）。后训练里现在主要用 RL（强化学习：让模型自己试着做任务，按结果好坏打分，再据此调整模型）。Infra（支撑训练和运行模型的底层系统）是这两个阶段都要依赖的底座；RL Infra 就是专门支撑强化学习训练的那一套系统。

- **预训练和 Infra**：应该把很多事前置，提早规划。
- **后训练**：现在要和 Agent（能自己分步骤、调用工具完成任务的 AI 程序）一起迭代，很多事没法提前规划清楚。它考验的是：能不能抓住当下模型能力和 Agent 这套做法之间的「化学反应」，并很快设计出新的 RL Infra。

**两代 RL Infra 的区别**：

- 针对 Code 和 Math 的推理（Reasoning，模型先想很久再给答案）阶段，RL Infra 的核心是推理引擎（让模型跑起来、生成回答的那段程序），因为模型要想很久再给出一个答案。系统围绕 rollout（训练中模型实际把任务试做一遍、产出完整过程）来搭。
- 针对 Agent 的 RL Infra 不只管模型推理，还要管模型和 Agent 框架（包在模型外面的程序，负责给模型喂信息、调工具、管理多个步骤）怎么配合。系统从「以推理引擎为核心」变成「以 Agent 为核心」，更复杂，可能是黑盒也可能是白盒。

### 第二版

**二、后训练跟着 Agent 一起迭代，RL Infra 的重心变了**

后训练（在基础模型上进一步训练，让它学会具体任务和行为的阶段）不一样：它现在和英尽（存疑）耦合在一起迭代，很多事没法提前规划清楚。这时更考验团队能不能抓住「当下的模型能力」和「这套 Agent（能自己调用工具、分多步完成任务的 AI 程序）范式」碰撞出的变化，快速设计新的 RL Infra（为强化学习训练搭的计算系统；强化学习是让模型反复尝试、按结果好坏得到奖励来改进）架构。

她对比了两个阶段的 RL Infra 要解决的问题：

- **面向 Code 和 Math 推理的阶段**（她称为 Chat 时代、做 Chat 加 reasoning 的时代，原话里「恰的形态」（存疑））：RL Infra 的核心是模型的推理引擎（让模型生成回答的那部分运行系统）本身，因为模型要推很长、思考很久，才给出下一个答案。
- **面向 Agent 的阶段**：不只关注模型推理本身，还要关注模型和 Agent 的耦合。重心从 rollout（模型在训练中实际跑一遍、产生回答或操作的过程）的推理引擎，转到以 Agent 为核心的、更复杂的系统，这个系统可能是黑盒（看不到内部、只能看输入输出），也可能是白盒（内部可以看到和改动）。

两个阶段要解决的 Infra 问题完全不一样，所以团队需要更敏捷，快速开发适合当前阶段的 RL Infra 系统。她列出这套系统面临的几个难点：

- **兼容性**：Agent 框架变化太快，系统要能兼容各种框架。
- **自适应或迭代**：如果真要涉及自适应或迭代，这套系统会难得多。
- **容错**：系统要有足够好的容错能力（某部分出错时整体还能继续跑）。
- **资源的综合管理**：同时涉及推理和训练，还要统一管理 GPU（擅长大规模并行计算的芯片，训练和运行模型主要靠它）和 CPU（电脑的通用处理器）。

她认为团队的敏捷性，以及 Infra 和研究之间的配合，是非常关键的事。配合得好，直接体现为研究速度明显变快。

## 5. 算子（训练排查时）

访谈 1T 模型训练稳定性一节。

### 旧版

- 原因可能是结构：比如稀疏比太高，full attention 层和 sliding window 层输出的数值差异很大，导致数值不稳定。
- 也可能纯粹是 Infra bug：比如某个通信算子写错了，甚至某个 norm 有问题。
- 实在没办法时：数值太大就 clip（截断）掉，或者用 norm 压下去。她认为用 norm 压肯定对模型效果有损。他们也借鉴了 Kimi 的 QK clip：QK 的某些 logits 非常大、影响训练稳定时把它截断，让训练先继续，进入稳态后再放开。

### 新版

1. **先发现问题**。很多团队把 loss spike 当正常现象，她们尽量做到没有 loss spike。理由是有 spike 就说明某一步参数更新特别不稳定，异常大的数值可能直接把某些参数或专家「打死」，也就是之后再也没有 token 被送到这个专家。所以需要一套严密的监控系统，至少要看专家负载、每一层的输入输出、激活值有没有异常。她说不是所有团队都会看这么细。
2. **再找原因**。可能是结构问题，比如稀疏比太高，导致全注意力层和滑动窗口层的输出在数值上差异很大；也可能纯粹是 infra 的 bug，比如通信的某个算子写错了；甚至可能是某个 norm 上有点问题。排查时会从表层一路查到底层，会怀疑是不是哪张卡坏了，所有卡都查过没问题，甚至会怀疑是不是太阳黑子爆发了。
3. **最后解决**。实在没办法时，数值太大的层要么直接截掉超出的部分（clip），要么通过 norm 把数值压下去。她认为压数值肯定会损害模型效果。也会借鉴 Kimi 的 QK clip：注意力里某些数值大到影响训练稳定时，只能先截掉，让训练继续，进入稳态后再放开。

### 第二版

**一、训练中遇到问题怎么办：先发现，再找原因，最后才用临时手段压住**

罗福莉把训练中处理问题分成两步：先**发现问题**，再**找原因**。找不到更好的办法时，才用 clip 这类临时手段让训练继续。

下面几个词说的都是大模型训练过程中数值出异常这件事：loss（训练时衡量模型预测错得多厉害的数，训练正常时会慢慢往下走）；Lost Spike（即 loss spike，loss 曲线突然往上跳的一下）；expert（MoE 模型里的"专家"，模型分成很多小块，每个词元只交给其中几块处理）；token（模型处理文字的最小单位，大致是一个字或词的一部分）；激活值（模型每一层算出来、交给下一层的中间结果）。

**发现问题：别把 loss spike 当正常现象**

- 她说很多团队把 Lost Spike 当成很正常的事，她们团队会尽量让训练里没有 Lost Spike。
- **理由**：她们认为有 Lost Spike，肯定会让某一步的参数（模型里训练时不断调整的数字）更新特别不稳定。某些数值异常地大，可能直接把某些参数或某些 expert "打死"。
- **"打死"的意思**：这次参数更新之后，再也不会有 token 被送到这个 expert 上，这个 expert 从此不起作用。
- 所以训练中需要一套很严密的监控系统，用来看清模型参数内部到底发生了什么变化。她举的最低限度要看的东西：
  - expert 的负载（每个 expert 分到多少 token，是否失衡）；
  - 每一层参数的输入和输出是什么样；
  - 激活值有没有变得很异常。
- 她说这些是 Northback（存疑）发生之后应该去查的。不是所有团队都会看这么细，好多人甚至不把它当成问题。

**找原因：结构问题和工程 bug 都可能**

发现问题之后，再去想到底是什么原因导致的。她举了几类：

- **结构原因**：比如稀疏比（模型里用 Sliding Window 层和用全局注意力层的比例，我的理解）太高。这会让负荣输出（存疑，可能指全局注意力层的输出）和 Sliding Window 层（每个位置只看附近一段文字的注意力层，计算更省）的输出至少在数值上差异非常大，这么大的数值差异会造成数值不稳定。
- **infra bug**（转录为 "infer bug"，指训练所用底层工程系统里的程序错误）：比如通信用的某个算子（底层的一个计算或数据传输函数）写错了。
- 她说她们最后发现，甚至可能就是某个 long 上（存疑）有点问题。

**实在没办法时的临时手段**

- 实在没办法的时候：发现某一层数值太大，要么把它 clip 掉（超过某个上限的数值直接截到上限），要么通过 lom（存疑）把它压下去。她说解决方案有非常多。
- **取舍**：她认为通过 lom（存疑）压下去肯定会损害模型效果。clip 是另一种方式。
- **例子**：她们也会借鉴 Kimi 的 QK clip。当 QK（注意力计算里用来算"该关注哪些词"的两组数值）的某些 notice（存疑，可能指 logits，即注意力打分）非常大、实在影响训练稳定时，没办法只能 clip 掉。这样至少能让训练顺利往下进行，等训练进入稳态（loss 平稳下降、不再频繁出异常）后，再把限制放开。
- 她总结说这类临时处理太多了，要去发现问题、解决问题，甚至倒推很多（这句话在本段结尾处断开）。
