# 先通查原片，再按剪辑地图剪（讨论中）

状态：讨论中，未定稿，不按这份动手。2026-10-15 王愉超提出。

## 想解决的问题

现在剪气口时只知道音量，不知道录像讲了什么。会后多录的尾巴、被检测成人声的环境音、无声但画面关键的片段，都要读懂内容才能判断。现在只能事后补救：剪完、转录完再裁结尾（决策记录 2.6），同一个视频改两次。

## 现在的流程（2026-10-15）

1. 找空白、剪空白：只看音量，拿不准的逐处量，夹在空白里的短碎片用人声检测器判断（决策记录 2.1、2.5、2.7）。
2. 导出剪后视频：本机有硬件编码器就用硬件编码（3.10）。
3. 转录剪后视频：字幕时间天然对得上剪后视频。
4. 裁结尾：模型读转录稿判断会在哪里结束，剪后视频和转录一起截短（2.6）。
5. Claude 看剪后视频的画面和转录稿写笔记，查漏，整理进产出文件夹。

## 讨论中的新流程：先通查原片，画出剪辑地图，再只导出一次

换顺序的目的（王愉超，2026-10-15）：动手剪之前先把原片通查一遍，知道哪里该去、哪里该留，尤其是无声但画面关键的片段。转录只是通查要用的材料之一。

1. 程序量出能量化的（不剪任何东西）：
   - 声音：哪里安静、多安静，哪里检测到人声，哪里是持续的环境噪音；
   - 画面：哪里在变（滚动、打字、翻页、切窗口），哪里静止；
   - 文字：转录原片，每句话、每个字的时间。
2. Claude 或用户自己的 agent 读这条合在一起的时间线，按上下文给出剪辑地图：每一段标"去除""保留"或"加速"，写明理由。例：
   - "大家看一下这页 PPT"之后安静、画面停在 PPT 上 → 保留，是给观众读的时间；
   - "我来演示一下"之后安静、画面在动 → 保留或加速；
   - "稍等我连一下""能听到吗"之后的安静 → 去除；
   - 检测到"人声"但转录里没有有意义的字 → 环境音，去除；
   - 会后多录的尾巴、整句重复的废话 → 去除；
   - 普通气口停顿 → 去除。
3. FluentFlow 检查地图（原片不动、不许剪掉太多说话），只导出一次视频。
4. 把字幕时间换算到剪后视频上。
5. 写笔记、查漏、整理文件夹，和现在一样。

分工：机械的测量、导出、核对由程序做；要读懂内容的判断交给模型。模型不逐个判断几千处空白：程序先处理明显的，只把拿不准的成片、内容层面的问题和"无声但画面在变"的片段交给模型。

控制成本：两小时的转录稿约四万字，可以整份给；画面只给"无声但画面在变"的片段各截几帧，不给整段视频。

## 截图

通查沿用产品现有的两种截图方式，不另起一套：

- 画面明显变化时截一张（PPT 换页、切窗口）。实测 15 分钟会议 79 张不重复画面，69 分钟课 97 张，约一小时一百张。
- 文本模型读转录稿，提出哪里需要截图（最多 8 处），再由模型从该时间段的候选帧里挑一张。

两种一起用：最有用的截图常常是转录稿没提到的（端口号、目录页、被转录听错的模型名），演示操作时讲者也常不说话，所以换页截图保证不漏，读字幕截图负责找准位置。

截图按用途分开：

- 判断剪不剪：只看"无声但画面在变"的片段，每段几帧（周二会议只有 4 段）。
- 写笔记配图：换页截图加读字幕截图，最后由模型挑出真正放进笔记的几张。

量在模型承受范围内（2026-10-15 查 Claude 官方文档）：一次请求最多 600 张图，超过 20 张时每张长边不超过 2000 像素；一张 1080p 约 2700 个视觉单位，上下文约放得下三百多张；约 1 美分一张。张数再多时先拼成缩略图墙粗看，再对挑中的看原图。

裁剪：模型说要哪块区域（例：只留共享屏幕，去掉参会人头像栏），程序找准边界再裁。模型给的框位置是大概的，不直接用它的坐标。

字词级的重复（"那那那"）先不剪：转录的逐字时间会偏几百毫秒，剪口落不准（决策记录 2.4）；第一版只处理整句的重复。

## 代价

- 字幕时间要换算：转录的是原片，剪掉空白后每句话都要按"它前面一共剪掉了多少"往前挪；一句话横跨一处剪口要缩短；剪口不能切进半个字。当初选先剪后转录就是为了省掉换算。缓解：产品已有换算代码；转录给出每个字的时间，剪口只落在字和字之间；导出后抽查几句字幕的位置。
- 转录对原片做，比剪后视频长，慢多少要实测。
- 每条多一次模型调用（约一两分钟），短视频可以跳过。

## 已定（王愉超，2026-10-15）

- 剪辑地图不给用户看、不让改，由模型默认执行。界面复杂度太高。
- 高风险的几处在整个任务完成后告诉用户，请他确认，例："我剪掉了原片 13:52 之后的 24 分钟，判断是会后多录的，你确认一下是不是有这么大段的空白。"时间用原片的时间。
- 页面样机（分支 `mock/cut-confirm`，网址加 `?mock=cut-confirm`）：任务卡片上一块"有 N 处剪得比较多，请确认"，每条写原片时间、剪掉多长、理由，三个按钮："在原片里听这段""剪得对""这段不该剪"。"剪得对"收成一行、可撤回；全部答完整块变灰。两种回答都记下来，用来检验模型判断准不准、给案例库当素材。主路仍是 agent 对话，页面是给不用 agent 的人。
- 待确认：高风险的界定（单独一段超过 1 分钟；被剪部分里有转录出来的字；开头或结尾整段裁掉），以及撤销口（倾向只在这几条提醒旁各放一个"这段不该剪"，点了按保留这段重新导出一次，不重新转录；用 agent 的用户直接对 agent 说）。

## 还在讨论

- 无声但画面关键的片段（讲者不说话在演示、滚动文档、写代码、写白板）怎么识别、剪还是留。
  - 实测周二会议：1.5 秒以上被剪的空白 24 段，画面在变的 4 段共 38 秒；最长 31 秒在会议开头（等人、切窗口、开录屏软件），剪掉是对的。
  - 发现靠程序（已有测画面变化的代码），判断是不是关键内容要交给 Claude 看几帧截图；程序分不出"切窗口"和"默默演示"。
  - 处理除了留和剪，还可以加速播放（30 秒演示压成几秒），这是新能力。
