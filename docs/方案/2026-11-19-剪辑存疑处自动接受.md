# 剪辑存疑处要不要自动接受

2026-11-19 · 王愉超提出，product-lens 评估（只有自评，见文末）· 状态：等他定

## 他的想法

剪气口后处理说明里「N 处待你判断」的条目，他判断过的从没改过，AI 判断得准，以后直接接受就好。顾虑是他用的 AI 强，别人换个弱的未必行。提议：检测到用户多次连续点「接受」，就关掉让人判断这一步，全部默认接受。

## 现在是怎么运作的（按代码核对）

- 「需要你判断」一组有两种来源（`backend/core/cut_report.py` `_with_judgement`）：
  - **规则必问**：去掉的是有人说话的段落、一整段剪掉超过 1 分钟、模型想去掉但被程序拦下的。不管模型多有把握都问。
  - **模型拿不准**：判断方自己标了 `unsure`，并写明拿不准在哪。
- 判断方有三类，记在 `survey.judged_by`：FluentFlow 自己找的 Claude 订阅（`claude_code_subscription`）、文字模型（`text_model`，如 DeepSeek）、用户自己的 agent（`agent:<它自报的模型名>`）。agent 的模型名是它自己填的字符串，Codex 填过 `codex-current-session`，看不出是哪个模型。
- 回答方式（`CutReport.jsx`）：每处「剪得对 / 确实该保留」（只记下，不重新导出），「这段不该剪 / 这段应该剪掉」（改判，重新导出、重写笔记，进回收箱可撤销），还有一个「剩下的都没问题」一次接受整组。
- **接受不改变产出**：剪辑在出说明之前已经按判断方的决定剪好了。没回答的条目只有两个后果：处理记录上一直挂着「N 处待你判断」；它不会变成案例。
- 案例（`backend/core/cut_cases.py`）：用户点过的接受和改判，最近 40 条交给下一次判断剪辑和整理说明的模型参考。只有用户点过的才算。
- 决策 6.11 当时已写下「毕业条件和起草剪辑规则等攒到真实点击再做」，他这次提的就是这个毕业条件。

## 证据（2026-11-19 只读查本机任务库）

**事实**

| 他的 agent（Claude） | 23 | 44 / 9 | 47 | 0 | 6 |
| 他的 agent（Codex） | 2 | 29 / 0 | 18 | 0 | 11 |
| 他的 agent（GPT） | 10 | 3 / 0 | 0 | 0 | 3 |
| FluentFlow 的文字模型 | 2 | 3 / 0 | 3 | 0 | 0 |
| 合计 | 78 | 144 / 14 | 105 | 0 | 53 |

- 158 处存疑里 144 处是规则必问（几乎全是「去掉了有人说话的段落」），模型自己拿不准的只有 14 处。
- 改判一次都没有，回收箱全空。
- 21 条任务还挂着没回答的条目，共 53 处。
- 接受都是他在网页上点的：Claude Code 和 Codex 的对话记录里没有 agent 调用过 `answer_cut_decisions`。
- 很多接受是批量的：「剩下的都没问题」一次点掉过 15、18、7、4 处；10-28 上午 11:09 到 11:12 三分半钟里，7 条任务共 51 处接受完，平均每处约 4 秒。

**判断**

- 0 次改判说明他没发现过剪错，但不能直接当成「AI 判断准」：一大半接受是批量点的，几秒一处，来不及逐处看画面。这份证据同时符合「AI 准」和「这一步他其实没在认真看」两种解释，两种解释都指向同一个结论：这一步对他来说是负担，不是在挡错误。
- 弱模型那边没有数据：GPT 和文字模型加起来只有 6 处，看不出准不准。
- 问得最多的是规则必问，案例机制让模型「越来越有把握」，但管不到规则必问，所以 6.11 设想的「以后要问的越来越少」在这部分不会自己发生。

## 几种做法比较

| 做法 | 对他 | 换了弱模型的用户 | 风险和代价 |
|---|---|---|---|
| A 不做 | 继续挂着 N 处待判断，21 条已经积着 | 不变 | 提示越积越多就没人看，真出错时也一样被忽略 |
| B 他的提议：连续接受 N 次后全局关掉 | 很快不用再点 | 换模型后照样默认接受，没人提醒；他之前对 Claude 的信任被记到新模型头上 | 连续接受很容易被「剩下的都没问题」凑满；关掉后没有办法自动重新打开 |
| C 按判断方分别攒记录，够了才对这个判断方默认接受 | 用 Claude 判断的任务（自带订阅和他的 Claude agent）立刻满足条件，不再问 | 新的或没记录的判断方照常问，攒够才放 | 判断方要能可靠认出来；agent 自报名字不可靠的，永远不放 |
| D 一律默认接受，只保留事后改判 | 不用再点 | 弱模型剪错了也没人提醒 | 剪掉的说话在剪后视频和笔记里都没有，用户不看就不会发现 |
| E 设置页给一个开关 | 他自己开 | 默认关，别人不受影响 | 多一个设置；开了以后和 D 一样，换模型也不提醒 |

外部做法：机器判断加人工复核的系统常见的做法是按置信度分流，低于门槛的送人工，高于门槛的直接通过，再随机抽一小部分已通过的给人看，用来发现模型变差（如 AWS 的 Amazon Augmented AI 的人工复核触发条件；有出处，未核原文）。C 就是这个思路，门槛按「这个判断方在这台机器上被用户改判过几次」定，而不是按模型自报的把握（模型自报的把握不算准确度）。

## 建议：C，具体这样做

1. **按判断方记账**。判断方按 `judged_by` 归一：FluentFlow 的 Claude 订阅、agent 自报的 Claude 系列算一类「Claude」；其余按名字各算各的；自报名字认不出模型的（如 `codex-current-session`、空的 `agent`）不放行。
2. **放行条件**（先定一个，之后看数据调）：这个判断方在至少 5 条任务里被回答过、累计至少 30 处、最近 30 处里没有一次改判。按现在的数据，Claude 一类满足（84 处接受、0 改判），Codex、GPT、文字模型都不满足。
3. **放行后怎么显示**：处理记录上不再挂「N 处待你判断」；处理说明里那一组改名为「AI 判断的，默认照它的」，照常展开、照常能改判，开头一句话写明「这台电脑上你确认过这类判断 N 次、没改过，所以没再问你」。不悄悄隐藏，只是不再当成待办。
4. **默认接受的不进案例**。只有他亲手点过的才进案例，否则模型会拿自己的判断当用户的确认，越来越自信。
5. **改判一次就收回**。被放行的判断方有一处被改判，就回到逐处询问，直到再攒够；页面写明「你上次改过这类判断，这次请你再看一下」。
6. **已经积着的 21 条**：上线时，属于已放行判断方的条目按第 3 条改显示，其余照旧。

为什么不选 B：B 的计数是按人算的，他换模型、别的用户装上用 DeepSeek，都会继承他对 Claude 的信任，正好是他自己担心的情况；而且「剩下的都没问题」一点就能凑满连续次数。为什么不选 D、E：剪掉的说话在剪后视频和笔记里都不存在，用户不回头看原片就不会发现，这种错看不出来，所以不该对没有记录的判断方默认放行。

C 的代价：要多维护一份按判断方的统计，判断方的名字要归一；agent 自报名字不准时会多问（偏安全的那一边）。

## 错了怎么办（改判的代价）

- 改判会从原片重新导出、重写笔记，要几分钟；回收箱里能撤销。
- 原片已经删了的，重新导出只能用存着的声音（6.11 意外情况），画面回不来。所以放行只针对有记录的判断方，弱模型照旧要人看。

## 证据不够的地方和怎么补

- 没有一次改判，放行门槛（30 处、5 条任务）是自定的，没有依据。补法：上线后记下放行后他主动去改判的次数，出现一次就回来看门槛。
- 批量接受时他看没看画面无法区分。补法：不补，C 不依赖这个，靠「改判一次就收回」兜底。
- 弱模型准不准没有数据。补法：C 本身就是让它攒数据的办法。
