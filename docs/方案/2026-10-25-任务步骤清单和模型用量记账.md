# 任务步骤清单和模型用量记账（方案，王愉超 2026-10-25 确认）

2026-10-25 · 接待办「任务『完成』指每一步都做完」（2026-10-18 王愉超定）和「文字模型每一步花了多少查不到」（2026-10-25 记）

两件事放在一起设计：用量要按「哪个任务的哪一步」记，而「现在在做哪一步」正是步骤清单要提供的信息。

## 现在的样子

**任务状态。** 任务表只有一个状态字段。转录稿存好时就写成「已完成」，之后的事都在这个「已完成」下面接着跑：等用户的 agent 判断剪辑、判断剪辑并导出、写笔记、压缩一份副本、发飞书、放进产出文件夹。每一步的进度各自存在任务结果里的不同字段：剪辑看 `debreath.status`，笔记看 `summary_status` 和看图笔记自己的状态。

所以「这个任务还在不在忙」有四处各自判断，规则也不一样：

- 删除和转录纠错前的检查（`task_activity.busy_reason`），里面还有一个「笔记交接期 120 秒内算忙」的猜测；
- agent 等任务（`local_agent._task_done`，看笔记、看剪辑）；
- 重启前的计数（`launchers/macos/count_active_jobs.py`，看状态、看笔记、看剪辑）；
- 页面上的状态标签（决策 6.23，按结果改了显示，后台没动）。

每加一个步骤，这四处都要再补一次。

**重启。** 启动时把「排队中、处理中」的任务标成失败，再用重试的路径**新建一条任务**整条重跑，从下载或导入、转录开始。已经「完成」、但剪辑或笔记正在跑的任务，剪辑和笔记分别被标成失败，要用户自己重新发起。

**取消。** 只在转录阶段有效，转录完任务已是「已完成」，取消返回 409。

**用量。** 模型调用从三种出口发出：

- DeepSeek、OpenAI、通义千问这类接口，走 `ai_client`（两处），已经接了一个记用量的挂钩，本地版的挂钩什么都不做；剪辑判断用设置里的看图模型时绕开了它，直接调接口；
- 用 Anthropic Key 调 Claude：`claude_vision`、`claude_text`、`cut_judge` 三处各自调；
- 用 Claude 订阅：都经过 `claude_code_note` 里同一个启动命令行的函数。

只有 Claude 写笔记那条路把用量存进了任务结果，其余都丢掉了。

数据库里有一张 `job_steps` 表（每步一行，有状态、开始和结束时间、失败原因、尝试次数），是托管版留下来的，本地版从来不写它；任务详情页的时间线会读它，读不到就从事件日志推。

## 要做到的

1. 每个任务一张步骤清单，每一步记「没开始 / 在做 / 做完 / 失败 / 跳过 / 停下」。
2. 任务状态只由清单算出来：有一步没到终点就是「进行中」，每一步都到了终点就是结束。结束分三种说法：全部做完；完成，但某一步失败（给重做这一步的入口）；已停下（给接着做的入口）。
3. 「这个任务还在不在忙」全产品只有一处判断，上面四处都改成问它。
4. 重启后在**原来那条任务**上，从中断的那一步接着做，做完的步骤不重做。
5. 任何一步都能停下，停下的那一步以后可以接着做。
6. 转录稿一存好就能看、能改，不等后面的步骤。
7. 每次模型调用记一条：哪个任务、哪一步、哪个服务商和模型、怎么付的钱（Key 还是订阅）、输入和输出的 token、其中命中缓存的部分、耗时、成没成功。处理记录里能看到每一步花了多少。
8. 记不到任务或步骤的调用也要记下来，标成「没归到步骤」，不丢。

## 怎么做

### 步骤清单

**用 `job_steps` 这张表，每步一行。** 理由：表已经在，详情页的时间线已经会读；每步单独一行，改一步的状态不用把整个任务结果读出来再写回去（现在多处改任务结果时要互相小心覆盖）。表里为托管版队列准备的加锁字段，本地版不用。

本地任务的步骤，按顺序：

| 步骤 | 包括 | 被打断后怎么接 |
| --- | --- | --- |
| 取素材 | 下载链接，或导入本机文件 | 重新取 |
| 转录 | 准备音频、本机转录、区分说话人 | 从头转（转录中途接着转不在这次范围） |
| 修正转录稿 | 画面字幕修正、词表纠错、英文录像的中文翻译 | 已记下改动的那一项不重做，其余重做 |
| 剪辑 | 等 agent 判断（开了这个选项时）、判断剪哪里、判断结尾、导出剪后视频 | 剪辑表已经存好就只重新导出，不再花钱判断 |
| 写笔记 | 挑截图、写、查漏 | 从头写（分段写时从写到的那段接着写，留到以后） |
| 压缩副本 | 高码率原片另出一份压缩版 | 重新压 |
| 发飞书 | 设置里开了才有 | 重新发 |
| 放进产出文件夹 | 把成品放到录像旁边的文件夹 | 重新放 |

用户没要的步骤（只要转录、没开飞书）在任务一建好时就写成「跳过」，所以「全部到终点」不用猜还会不会有下一步，`busy_reason` 里那个 120 秒的猜测可以删掉。

每一步由同一个函数包着跑：开始时写「在做」和开始时间，结束时写「做完 / 失败 / 跳过」、结束时间和失败原因，同时按步骤清单重新算任务状态，写回任务表的状态字段。任务表的状态字段保留，但只由这个函数写，列表、筛选这些旧代码照常读它。

**「还在不在忙」只有一处：** 一个函数读步骤清单，回答「在忙吗、在忙什么（用户看得懂的一句话）」。删除检查、转录纠错检查、agent 等任务、重启前计数、页面状态都调它。`/jobs` 接口给每个任务带上这个答案，重启前计数的脚本只数它。

**用到「已完成」的地方要一个个改成问具体那一步。** 例如：能不能改转录稿，看「转录」做没做完，不看任务是否结束；能不能重写笔记，看「写笔记」是不是在做。后端约 21 个文件、前端约 14 个文件里出现了按「已完成」分支的代码，每处都要过一遍。这是这次工作量最大、也最容易漏的一块，靠下面「怎么测」里按需求写的测试守住。

**重启。** 启动时不再把任务标失败、也不再新建任务。对每个没结束的任务：「在做」的那一步改回「没开始」，从第一个没到终点的步骤接着跑，排回队列。连续被重启打断两次以上的照现在的规矩留给用户，不自动再跑。

**停下。** 停的是当前那一步：转录停掉转录进程，导出停掉编码进程，写笔记停掉 Claude 命令行或放弃等待中的请求。那一步记「停下」，任务显示「已停下」，给一个「接着做」的入口，从这一步开始。

**旧任务。** 没有步骤清单的任务都已经结束（启动时那些没结束的会按上面的规则处理），照它们记录里的状态显示，不补写清单。

### 模型用量记账

**一张新表 `model_calls`，每次调用一行：** 任务、步骤、步骤里的哪一项（比如「剪辑 / 判断结尾」「写笔记 / 查漏」）、服务商、模型、付费方式（Key / 订阅）、输入 token、其中缓存命中的 token、输出 token、耗时、成没成功、时间。

**在出口记，不在每一步记。** 记账写在上面那几个出口里（`ai_client` 两处、剪辑判断直接调接口的一处、Anthropic Key 三处、订阅命令行一处），都调同一个记录函数，就是把现在 `ai_usage` 的挂钩扩成所有出口都用。出口只有这几处，加新步骤不用碰记账。

**「哪个任务的哪一步」怎么带到出口：** 包着每一步跑的那个函数，在开始时把任务和步骤放进当前上下文（Python 的 `contextvars`），出口记录时从上下文里取。要注意的是工作线程：`run_in_executor` 和自建的线程池不会把上下文带过去，所以凡是把活交给线程的地方，都改成连同上下文一起交（`contextvars.copy_context().run`）。漏了一处，那次调用会记成「没归到步骤」，在处理记录里能看到，不会悄悄少记。

**钱数在显示时算，库里只存 token。** 价格表放在仓库里，按服务商、模型、生效日期列每种 token 的单价；DeepSeek 按调用时间分高峰、非高峰两档。价格表里没有的模型只显示 token，不显示钱。走订阅的调用显示 token 和「订阅，不按次计费」；命令行自己报的折算金额只按「按 API 价折算」显示，不当成实际花费。

**在哪里看：** 处理记录页每一步一行，写用了哪个模型、调用几次、token 多少、约多少钱，顶上写整个任务合计。agent 取任务概况时带上合计和每步的数。

## 已定的取舍（王愉超 2026-10-25）

1. **价格表放在仓库里**，随版本更新；价格变了要发新版才生效。不放进每天从 main 读取的 `recommended_models.json`：那个文件出错会立刻影响所有已安装的用户。
2. **转录中途被打断从头重转**，这次不做中途续转。要续转得把本机转录改成分段存进度，工程量和这次差不多大；长录像被打断常见了再单独做。
3. **写笔记被打断整步重写**，这次不做分段写时从写到的那段接着写。

## 分几批做

1. **步骤清单和统一的「在不在忙」**（2026-10-25 已做，决策 6.41）。做成的样子和上面写的有三处不同：
   - 任务表的状态字段仍是「转录稿存好就是已完成」，没有改成由步骤清单写。很多入口（看转录稿、改字幕、重新剪辑、重写笔记）正是按「转录稿已经有了」放行，改掉它要动三十多个文件，用户看不到差别。「整个任务做完没有」由 `task_activity` 读步骤清单回答，删除、agent 等任务、重启前计数、处理记录页的状态、重新剪辑的两个入口都问它，`/jobs` 每条任务带上它的答案（`activity`）。
   - 这一批记五步：转录（含取素材和修正转录稿）、剪辑、写笔记、压缩副本、发飞书。取素材和修正转录稿单独成步放到第 2 批，续接时才用得上。放进产出文件夹不算一步：笔记每改一次它就重新同步一次，和任务做没做完无关。
   - 处理详情页的时间线仍从事件日志推，步骤清单放在它旁边（`steps`）；改成读步骤清单放到第 2 批。
2. **重启接着做、每一步能停下**（2026-10-25 已做，决策 6.42，交付记录 [2026-10-25-任务步骤清单第二批](../交付记录/2026-10-25-任务步骤清单第二批.md)）。转录拆成取素材、转录、修正转录稿三步；重启后在原任务上接着做；剪辑表存好的只重新导出；每一步能停下、接着做；详情页时间线读步骤清单。关服务时剪辑的 FFmpeg 不跟着停，留在待办。
3. **用量记账**：依赖第 1 批（要从步骤清单拿到当前步骤）。第 2 批把运行流程搬进了 `backend/core/task_flow.py`，「把任务和步骤放进当前上下文」放在那里每一步开始的地方；把活交给线程的地方，`task_flow` 已有一个 `_bound_to` 包装，可以顺带在那里复制上下文。

## 怎么测

测试按上面「要做到的」写，不照实现写：

- 一条只要转录的任务，转录存好时就是结束，不会一直显示进行中；
- 一条要剪辑和笔记的任务，在剪辑、写笔记时，删除被拒、agent 等任务不返回、重启前计数为 1、页面显示进行中，转录稿能看能改；
- 笔记失败时任务显示「完成，但笔记失败」，agent 等任务立刻返回，不一直等；
- 在剪辑导出中途重启服务，同一条任务从「剪辑」接着做，转录不重跑、不重新花钱判断剪辑，最后有剪后视频和笔记；
- 写笔记中途停下，任务显示「已停下」，点接着做从写笔记开始；
- 用假的模型出口跑一条完整任务，每次调用都有一行记录，而且全部归到了步骤，「没归到步骤」为 0。

都过了以后，复制一条真实录像的短片段（10 分钟左右），用他的 DeepSeek Key 跑一遍，在剪辑导出中途重启一次，核对：同一条任务接着做完；处理记录里每一步的 token 和 DeepSeek 后台当天的用量对得上。

## 重做需不需要原片

不需要。这次改的是以后的任务怎么记状态、怎么记用量；已经处理完的任务不受影响，也没有可补的用量记录。
