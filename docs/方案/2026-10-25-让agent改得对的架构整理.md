# 让 agent 改得对的架构整理

2026-10-25 · 接「产品架构优化方向」子对话的四条建议，王愉超要求先查清每条哪些已经做了、哪里做得不够，想清楚再做

FluentFlow 的代码几乎都是 agent 写的。agent 每次开工都从零开始：它找不到「这件事归哪里管」，就会在手边的代码里再写一份判断；改一个能力要动几处而没有检查，它就会漏改，而且不报错。下面四条都针对这两种情况。

## 1. 每件事在哪里决定：代码地图，加检查防止改回去

**已经做了的：** `AGENTS.md` 写了仓库边界、测试、文档、重启的规矩；界面样式有一处说了算（`frontend/src/lib/ui.js`），`frontend/src/ui-rules.test.js` 在页面自己写样式时报错。第 1 批把「任务还在不在忙」收进了 `backend/core/task_activity.py`。

**做得不够的：**
- 说明里没有代码地图。agent 要知道「剪哪里在哪定」「笔记谁来写在哪定」，只能自己搜，搜到哪处改哪处。
- 「在不在忙」只靠约定。现在仍有三处在 `task_activity` 之外直接读剪辑或笔记的运行状态：`local_job_debreath.py` 两处（同一任务一次只受理一个去气口）、`agent_note.py` 一处（笔记正在重写时不让 agent 写）。它们查的是「同一件事是不是已经在做」，不是「任务忙不忙」，可以留，但新代码再这么写时没有任何东西拦着。

**要做到的：**
- `AGENTS.md` 加一节「每件事在哪里决定」，一行一个概念、一个文件，并写明：改这些概念只改表里那一处，表里没有的新概念，做完把它加进表。
- 加一条后端测试：除了表里认可的文件，任何代码直接读剪辑或笔记的运行状态（`debreath_job.is_running`、`visual_note_job.is_running`），或拿笔记状态和 `"pending"` 比，测试就失败，提示去问 `task_activity`。现在已有的几处列进允许名单，每处写明为什么可以。

**不做：** 前端不加同样的检查。前端只剩 `taskState.js` 在后端没给答案时（旧缓存）兜底读笔记状态，一处，写在注释里。

**验收：** 表里每个文件都真实存在（测试里核对）；往一个新文件里写 `debreath_job.is_running(...)`，测试失败并说该去哪里。

## 2. 对任务的操作只写一处：和第 2 批一起做

**已经做了的：** 剪辑报告的三个操作，改判、确认、撤销，逻辑在 `backend/core/survey_cut.py`（`flip`、`verdict`、`undo_change`）；「不等 agent、FluentFlow 自己判断」在 `agent_cut.give_up`。agent 能用的去气口、重写笔记，走的是和网页同一个函数（`start_local_debreath`、`start_local_visual_note`），检查条件两边一致。

**做得不够的：**
- 这些共用的函数和检查放在网页接口的文件里（`routers/local_job_debreath.py`、`local_processing.py` 等），agent 的接口文件从五个网页接口文件里借函数。没被借过去的操作 agent 就做不了：改判、确认、撤销、取消任务，agent 至今都不能做（待办第 7、15 处）。
- 取消任务的逻辑整段写在网页接口文件 `local_job_mutation.py` 里。
- 「同一时间只渲染一个」「队列忙时不受理」的判断要问排队状态，排队状态放在 `local_processing.py`（全仓库最长、改得最勤的文件之一）里，谁要用都得引用这个网页接口文件。

**要做到的（第 2 批的范围扩成这样）：**
- 新建 `backend/core/task_actions.py`：对一个任务能做的操作，每个一个函数，接收任务和参数，做完返回结果，不能做时抛一个带原因（给人看的一句话和一个代号）的拒绝。共用的检查（任务在不在、在不在忙问 `task_activity`、队列忙不忙）都在这里。
- 排队状态从 `local_processing.py` 搬到 `backend/core/task_queue.py`，操作和网页接口都问它。
- 网页接口和 agent 接口只做一件事：把请求转成调用，把拒绝转成 409。agent 接口文件不再引用任何网页接口文件。
- 这一批搬进来并补给 agent 的操作：改判、确认、撤销、取消，以及第 2 批新加的「停下这一步」「从中断的那一步接着做」。MCP 加对应的工具，`agent/skills/fluentflow/SKILL.md` 写明什么时候用。
- 去气口、重写笔记、重试这些两边已经能用的，这一批不搬，以后改到哪个搬哪个。

**不做：** 不改任何操作的规则和提示语，网页上的按钮不变。

**验收：**
- 同一张用例表（任务状态、操作、预期结果或拒绝原因）分别从网页接口和 agent 接口跑一遍，结果一致。
- 一条测试：agent 接口文件不引用 `backend/routers/` 下的其他文件。
- 第 2 批原有的验收照旧（重启后在原任务上接着做、剪辑表已存好的不再花钱判断、停下后能接着做），再在真实数据副本上跑一遍。

**怎么做：** 这一批工作量大，会碰 `local_processing.py`，几个对话同时在改这个文件。开一个子对话，在单独的工作副本里分几次小提交做，每次提交前接一次最新的 main。

## 3. agent 工具的说明只写一处

**已经做了的：** `tests/test_mcp_tool_descriptions.py` 检查工具清单、工具函数和自检脚本三处一致，也检查几条关键描述（等任务会等剪辑和笔记、重做类工具写明不是常规路径）。

**做得不够的：**
- 给 agent 加一个能力要改四处：后端接口、MCP 里的函数（它自己的说明）、MCP 工具列表里的描述、`SKILL.md`。同一个工具在 MCP 文件里有两份说明，内容不一样也没人知道。
- 没有检查「后端加了 agent 接口、MCP 没给工具」：现在 32 个接口都有工具对应，是靠每次记得。
- 没有检查 `SKILL.md` 里提到的工具是否真的存在：改了工具名，skill 里的旧名字不会报错。

**要做到的：**
- 现在就加的检查：每个 `/agent/v1` 接口都至少被一个 MCP 工具调用，不需要工具的接口列进名单并写明原因；`SKILL.md` 里用反引号写出的工具名都必须存在。
- 第 2 批做完后再改结构：每个工具的描述只写在它的函数旁边，工具列表由函数生成，删掉第二份说明。操作集中以后，说明才有固定的地方可放，所以排在第 2 批之后。

**验收：** 往 agent 接口文件加一个新接口而不加工具，测试失败；把 `SKILL.md` 里一个工具名改错，测试失败。

## 4. 改得最勤的大文件，碰到时按功能拆

**已经做了的：** 编辑页拆出过 `editor-helpers.js`、`editor-dialogs.jsx`，测试也按功能分成了十个文件；任务的读、改、取消、去气口接口早已从处理接口里分出去。

**做得不够的：** 两个最热的文件还在两千行以上：编辑页 `frontend/src/routes/editor.jsx`（2223 行，两周改了 32 次，全仓库代码文件里最多）和处理接口 `backend/routers/local_processing.py`（2348 行）。几个对话同时改时冲突撞在这里：第 1 批合进 main 前后接了三次。没有一条规矩告诉 agent 碰到时顺手拆。

**要做到的：**
- `AGENTS.md` 加一条：改这两个文件时，先把自己要改的那块搬成单独的文件，再在新文件里改；写明各自可以拆的块。编辑页：顶部条、转录稿栏、笔记栏、播放和跟随。处理接口：排队（第 2 批搬到 `task_queue.py`）、各个提交入口、转录完之后的流程（剪辑、写笔记、压缩、发飞书）。
- 不专门安排时间拆，也不为拆而拆。

**验收：** 这一条是规矩，没有测试；第 2 批做完时 `local_processing.py` 应少掉排队和转录后流程两块。
