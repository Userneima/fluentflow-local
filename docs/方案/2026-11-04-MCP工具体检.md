# MCP 工具体检

2026-11-04 · 照 Anthropic《Writing effective tools for agents》查 `scripts/fluentflow_mcp_server.py`。只出清单，王愉超看过点头后再改代码。

## 结论

- 工具说明的长度在两个宿主上都不是主要问题：Claude Code 用工具搜索按需加载；Codex 也按需加载（下面「量法」第 4 条）。所以「删短说明」「合并工具」收益小，排在后面。
- 真正花上下文、偶尔出错的是**返回结果**：长录像的任务包超过 Claude Code 5 万字符的门槛被存成文件；`get_task` 九成是一张章节时间表；Codex 在约 1 万 token 处截断，连 15 分钟录像的写笔记材料都被截过。
- 报错大多已经写了下一步该怎么做，缺口在「任务不存在」这类通用错误上。

按收益从大到小。全部已做（2026-11-04）：第 1 到 3 条见决策 8.18，第 4 到 8 条见决策 8.20。

## 量法

1. 工具说明：`TOOL_DEFINITIONS` 逐个转 JSON 量字符数。46 个工具合计 55,500 字符（转 JSON 时中文不转义）。
2. 返回大小：在 8000 端口的真实服务上，只调只读的查询工具，对任务列表里 60 条有笔记的任务各量一次返回的字符数。取材料的四个工具会写标记文件、记步骤计时，没有调；写笔记材料的大小按任务包里的转录字数加写法说明估。
3. Claude Code 的门槛：本对话直接调 `get_task_package`，51,704 字符那条被存成文件；子助手调 26,292、34,697、43,701 字符三条，都原样收到。实测门槛是 5 万字符，不是 2.5 万 token（中文 4.3 万字符远超 2.5 万 token 也没触发）。原样收到不等于没成本：子助手调这三次用了约 15 万 token。
4. Codex：读本机 Codex 的对话记录（`~/.codex/sessions`，2026-10-13 到 10-29 用过 FluentFlow 的会话）。Codex 0.164 的桌面版走「代码模式」，工具在一段 JavaScript 里调用；发给模型的工具清单里没有任何 FluentFlow 工具的说明，只写「有些工具没列出，在 `ALL_TOOLS` 里按名字和说明找」，即按需加载。本机 0.166 的 `codex features list` 里 `tool_search_always_defer_mcp_tools` 为真。截断：约 300 次 FluentFlow 调用里有 12 次返回被截，提示为 `truncated output (original token count: N)`，N 从约 2,800 到 15,900；一次 15 分钟录像的写笔记材料（13,634 token）被截过。一段脚本里可能连调几个工具，截断记到哪个工具上是近似的。
5. 使用频率：Claude Code 对话记录（`~/.claude/projects`）里 FluentFlow 工具共被调用 937 次，`wait_task` 207、`submit_local_media` 127、`get_task` 107、`submit_video_link` 97、`write_note_from_cut_media` 61、`get_agent_note_material` 52、`get_task_package` 38；有 19 个工具一次都没被调过（多是 10 月下旬新加的转录修正、改判、复习笔记）。

## 1. 任务包去掉重复的大块

**现象**：60 条任务的任务包中位数 24,574 字符，最大 76,371。超过 5 万字符的 2 条（罗福莉访谈 3.5 小时 76,371、Agent 时代学习 51,704），在 Claude Code 里被存成文件，agent 要再分段读。超过 2.5 万的 28 条，在 Codex 里都会被截。最大那条的构成：笔记全文 45,703，章节时间表 15,372，产物清单 3,929，其余各一两千。

**建议**：

- 章节时间表从任务包里拿掉，只留一行概况（几节、几节有时间、缺哪几节的编号）。时间表的正本在 `get_agent_alignment_material`。随产品的 skill 读任务包和 `get_task` 的 `note_alignment`，只为看还有没有章节缺时间，概况够用；skill 里那两句跟着改成读概况。
- 给 `get_task_package` 声明 `anthropic/maxResultSizeChars`（和取材料工具一样，50 万），Claude Code 里再长的笔记也一次收到。
- 笔记全文照 5.9 的决定保留。「按节读、按节改」已记在 5.9 的「考虑过」里，等有 agent 修笔记的记录再定，这里不重提。

**收益**：最大那条从 76,371 降到约 61,000，加上声明后在 Claude Code 里一次收到；其余任务每次少几千字。Codex 那边笔记本身就超过它的截断线，这一条帮不上，见第 3 条。

**代价**：改任务包的生成（`backend/core` 里组任务包的那一处）、任务包版本号加一、更新相关测试和工具说明里的字段描述。

## 2. `get_task` 不再带整张章节时间表

**现象**：`get_task` 说明里叫「轻量状态」，60 条任务中位数 5,399 字符，最大 16,533；最大那条里 15,532 是章节时间表（每节的标题、编号、起止时间、其他出处）。它是 Claude Code 里调用第三多的工具（107 次），Codex 里也调了 33 次，每次都把这张表带进对话。

**建议**：和第 1 条一样，只留一行概况。agent 判断「还要不要对齐」只需要「有几节没时间」，`wait_task` 的 `next` 已经会提醒。

**收益**：长笔记的任务每次 `get_task` 少约一万字，等于每次调用省下几千到一万多 token，对话里调几次就省几次。

**代价**：小。和第 1 条共用一个概况函数（后端 agent 路由里任务包和 `get_task` 两处都调 `note_section_times.status`），改 `SKILL.md` 第 68 到 70 行的说法和相关测试；页面不走这个接口。

## 3. 写笔记、剪辑材料在 Codex 被截断时告诉它怎么读全

**现象**：`anthropic/maxResultSizeChars` 只对 Claude Code 有效。Codex 在约 1 万 token 处截断，60 条任务里写笔记材料超过约 9 千字的有 28 条（转录中位数 4,000 字、最大 67,814 字，加约 4 千字写法说明）。记录里 Codex 自己把结果存进变量再分段读，读到了，但多花了几轮；它也可能只读开头就动笔。

**建议**：取材料两个工具的说明和返回开头各加一句：结果被宿主截断时，从保存的结果里分段读完，或带 `small_parts=true` 重取。返回开头再给一个总字数，让 agent 能核对自己读全了没有。

**收益**：Codex 用户读漏转录的风险降低，少几轮试错。

**代价**：很小，两处说明加一句、返回加一个字段。效果只能在 Codex 上实际跑一次才知道（走 Codex 订阅，不按量计费）。

## 4. 转录修改记录默认不列已撤回的，两组工具合成一组

**现象**：`list_glossary_corrections` 没有分页，60 条中位数 229 字符，最大 92,950（黑客级调研 kickoff，244 条修改），超过 5 万字符被存成文件。这 244 条里 122 条已经撤回，占 46,769 字符；每条还带前后两句（共 8,583 字）和词表原文（7,432 字，同一行词表在多条里重复）。`list_subtitle_corrections` 最大 46,791。两组工具（列出、撤回各两个）结构相同，只是来源不同。

**建议**：

- 默认只列还生效的，返回里给已撤回的条数；带 `include_reverted=true` 才列出来。词表原文按行去重，放一张表，每条只写行号。
- 合并成 `list_transcript_corrections(task_id, source)` 和 `revert_transcript_corrections(task_id, source, ids)`，`source` 取 `subtitles` 或 `glossary`。这正是文章说的「把总是成对、只差一个参数的工具合成一个」。

**收益**：最大那条降到约 4 万字符以下，一次收到；工具从 46 个减到 44 个。

**代价**：中。工具改名要同时改 `SKILL.md`、决策记录里引用的地方（4.x 的条目照旧保留旧名，写新条目说明）、`tests/test_agent_surface.py` 和 `save_agent_correction` 说明里提到的撤回工具名。agent 每次开对话都重读工具表，旧名不用留兼容。

## 5. 报错和返回里的下一步补齐

**现象**：

- 好的部分：多数拒绝已经带 `code` 和中文说明，说明里也写了每个 `code` 怎么办（`resume_task`、`flip_cut_decision`、`restore_note_version` 等）。比如读不存在的版本，回「先列出历史版本，用列表里的 version_id」。
- 任务编号写错时，`get_task`、`get_task_package` 回英文「Job not found」，没有下一步；`get_cut_report` 回「任务不存在」，也没有。agent 最常见的错就是编号抄错或只抄了前 8 位。
- 每个错误的说明出现两次（`error` 一份、`payload.detail` 一份）。
- `list_tasks` 传 `limit=200` 只回 100 条，不说还有更多；`limit` 传成字符串时报 Python 原话 `invalid literal for int()`。
- `wait_task` 和提交工具的回复带 `package_url`（`/agent/v1/tasks/…/package`），这是 HTTP 地址，agent 用不上，该写「用 get_task_package 读」。
- 对一条早就做完的任务调 `get_agent_cut_material`，回「已经改由 FluentFlow 自己判断：agent 的对话已经关掉了」，实际是这条任务根本不在等剪辑判断。

**建议**：任务不存在统一回中文「没有这个任务（编号要完整的 32 位）。用 list_tasks 按标题找」；错误只放一份；`list_tasks` 回 `has_more`，参数类型错时回一句说清该传什么；`package_url` 换成工具名；剪辑材料在任务不等判断时说「这条任务现在不需要判断剪辑」。

**收益**：agent 出错后少猜一轮。每条报错也短一半。

**代价**：小，集中在 `_agent_request` 和后端 agent 路由的几处。

## 6. 处理说明默认只给要看的几节

**现象**：`get_cut_report` 中位数 6,505 字符，最大 38,231，超过 2.5 万的 3 条。最大那条里「其他处理」一节 194 项、31,249 字符，占 82%；用户要看的「需要你判断」只有 9 项、2,174 字符。

**建议**：默认给「需要你判断」和保留、剪掉的较长空白，其余几节只给项数；带 `section` 取某一节全部。

**收益**：长录像的处理说明降到约 6 千字。它目前只被调过 2 次，所以排在后面。

**代价**：小。`flip_cut_decision` 用的 `ref` 不变，只是有些 `ref` 要多取一次那一节才看得到。

## 7. 两个提交工具的说明删短，`api_base` 从参数表拿掉

**现象**：`submit_video_link` 说明 2,003 字符（连参数 3,970），`submit_local_media` 1,653（3,390）。两者共用一段 1,400 字的流程说明，里面有几句模型用不上：「后台可能用 Anthropic Key、本机订阅或文字模型」、「本地版才收、后端只收本机来的」、`note_mode` 等三项只在文字模型写时生效（参数表里已经写了）。46 个工具都带 `api_base` 参数，没有说明，agent 从来不需要传。

**建议**：流程说明保留这些约定，其余删掉：

- 默认由当前 agent 判断剪辑、写笔记，配了 Key 也一样，不要等 Claude 先失败；
- 提交后立即返回，接着调 `wait_task`；它会在要判断剪辑、可以写笔记、要修正转录时返回并在 `next` 里说下一步；
- 只在 agent 做不了、失败了或用户要求时用 `intelligence=fluentflow`，并告诉用户用的是谁的额度；
- 一次一个文件；链接的重复规则（这段只在 `submit_video_link` 里）。

`api_base` 从每个工具的参数表里拿掉，函数照旧收（测试和指向别的端口时用环境变量 `FLUENTFLOW_API_BASE`）。

**收益**：两个提交工具各短约 800 字，46 个工具合计少约 2 千字。只在 agent 加载这两个工具时省下，所以收益小。

**代价**：小。删之前对照 `SKILL.md` 确认被删的话在那里或 `wait_task` 的 `next` 里有；改后跑 `scripts/evaluate_agent_mcp.py`。

## 8. 取材料、交回两组工具不合并

四个 `get_agent_*_material` 和五个 `save_agent_*` 看着重复，但不建议合并：

- 每组的分页方式不同（笔记按部分、修正按固定句子范围和每页版本号、对齐按偏移量），交回的结构完全不同。合成一个工具，参数表就是几种结构的并集，模型更容易传错，说明也不会变短。
- 两个大材料工具单独声明了 50 万字符的返回上限，合并后其余几种也跟着放开。
- 文章说合并的是「总是连着调、中间不需要 agent 判断」的工具。`save_agent_cut` 之后一定接 `save_agent_cut_report`，但报告要用前一步返回的编号事实来写，中间正需要 agent 整理，也不合并。
- `debreath_task`、`write_note_from_cut_media` 和 `regenerate_note` 有重叠，但 6.53（2026-11-03）刚把提示指向 `debreath_task`，`write_note_from_cut_media` 历史上被调过 61 次，不在这次动。

## 改之后怎么验

- `scripts/evaluate_agent_mcp.py` 用写好的调用序列测工具（离线替身或接真实服务），不调模型，不花钱；在测试副本上跑（`scripts/prepare_test_copy.py --fake`）。
- 第 1、2、4、6 条改完，在 8000 上用本文的量法重量一遍，对比前后字符数。
- 第 3 条要在 Codex 里让它给一条长录像写一次笔记，看它有没有读全（走 Codex 订阅，不按量计费；写笔记的材料来自已有任务，在测试副本上做）。
- 想看 agent 会不会因为说明删短而走错路，可以让 Claude Code 子助手在测试副本上从提交走到存笔记一遍（走订阅，按以往一条 15 分钟录像约 15 分钟）。
