2026-11-26 · 子对话（T3 / OpenCode，deepseek-v4.1-flash）· 待办「可靠」里三条：Windows 上四路并行跑测试有几条偶发超时、Windows 测试修复补审的两条建议、下载视频的 yt-dlp 子进程也关掉标准输入

## 1. 改了什么

- **任务步骤的读写不在事件循环上**（决策 8.30）：`backend/core/task_steps.py` 给每个读写加了 `*_off_loop` 的异步版本，把这件同样的库调用交给工作线程做完再往下走；`task_flow.py`、`link_submission.py`、`task_queue.py`（`plan` 前的那次读）改成 await 它们。「这次模型调用算哪一步」是调用线程的 contextvar，留在调用线程上设。一次一次 await，所以同一条任务的两次写不并行，写完的读一定看得到；取消到来时先等已经交给线程的那次写完再让取消往下走，收尾不会和还在飞的写抢同一行。
- **流程异常结束时取消还在编码的压缩副本**：原来它在生产里会继续编码，结束时还把 `compress` 从 skipped/failed 改回 done。
- **测试的等待预算**：`test_task_steps.py` 里整条流程 5 秒、`test_task_resume.py` 10 秒、`test_task_entry_routes_http.py` 的 `_wait_until_done` 默认 5 秒，都改成 30 秒，只用来兜住卡死；「填产出文件夹不挡队列」改成把第一份的填充卡在门闸上，第二条任务做完时它还没结束，不再靠「3 秒够不够」。
- **测试断网守卫拦域名解析**（决策 8.31）：`tests/test_test_run_switches.py` 的 `reached` 同时拦 `socket.getaddrinfo`，只有本机地址放过；Windows 的 `ConnectEx` 也管住。
- **子进程不接终端**（决策 8.32）：`backend/core/video_source.py` 两处跑 yt-dlp 的 `Popen` 加 `stdin=subprocess.DEVNULL`；`scripts/run_service.py` 起 uvicorn 之前把 fd 0 换成空设备（Windows 启动器用它起服务）。
- **第一轮 Windows CI 之后补的**（同一次改动带出来的，都是固定等待或按线程算的旧假设）：`test_serial_queue_entries.py`、`test_pipeline_events.py`、`test_video_source_links.py`、`test_note_does_not_hold_queue.py` 里「起完任务等 0.2 到 10 秒再看日志」改成等那条日志出现；「最多两路同时下载」改成把下载卡在门闸上，等五条里有两条进来再看有没有第三条；数任务库打开次数的那条只数本线程的（同进程里别的测试留的线程也会打开）；`test_task_steps` 的 `FLOW_SECONDS = 30` 被 `test_no_speech`、`test_transcript_only_no_cut`、`test_compressed_copy`、`test_cut_and_note_side_by_side` 引用，替掉各自的 5 秒。重启后恢复的提示改成先撤掉、再收尾步骤（页面不会看到一条已经结束的任务还写着「服务重启后已从断点恢复」）。
- 文档：决策 8.30、8.31、8.32 和第八节现状；更新记录一条；待办删掉这三节；`AGENTS.md`「Where things are decided」里 `task_steps` 那行写明流程用 `*_off_loop`。
- 测试：`tests/test_task_steps.py::test_the_step_records_are_never_written_on_the_event_loop`、`tests/test_test_run_switches.py::test_the_guard_stops_a_name_lookup_on_every_platform`、`tests/test_ffmpeg_stdin.py` 里 yt-dlp 和 `run_service.detach_stdin` 各一条。

## 3. 没做的、没验证的

- Windows 上的两次 CI 只证明这套测试在 Windows 上不再偶发失败，没在真人 Windows 电脑上量过开始一条任务时网页卡多久。产品上「写库不在服务线程」是用 `test_the_step_records_are_never_written_on_the_event_loop` 守的，不靠 Windows 实测。
- `run_service.py` 的 `detach_stdin` 只在子进程里验证 fd 0 变成了空设备，没在真 Windows 上启动过服务；Windows 的进程服务本来就不给控制台，这次是让子进程不必依赖这件事。
- 把 SQLite 的锁等待从 5 秒放宽到 30 秒，是本机看到 Windows 上「database is locked」之后的判断，不是量出来的：没在 Windows 上量过锁一般等多久。真人电脑上的磁盘比 GitHub 的机器快，这一步只是让偶发的等待变成等待而不是报错。
- 没动的：`export_agent_note_if_asked` 里开始飞书那一步、重启时 `agent_cut_goes_on` / `resume_agent_exports` 的读、`transcript_note.py` 和 `task_actions.py` 里的单次提交（每次一笔，见 8.27），理由写在 8.30。
- Codex 推送前审查没跑：这次是子对话，按简报要求不推 main，由主对话在交付时决定怎么推。

## 4. agent 遇到的阻碍

- `say -o` 用默认（中文）声音生成的 aiff 只有 0.012 秒，`ffmpeg` 编出 864 字节的 mp4，服务直接报「没检测到人声」。换成英文文本（默认英文声音）就正常。要中文试听片段时得显式指定中文声音（`say -v '?'` 里有 Eddy、Flo 等）。可以在 `~/Projects/yuchao-agent-skills` 的平台文件里记一句「用 `say` 造试听素材时显式挑声音，默认声音读不了中文」。
- 第一次的 Windows CI 跑在临时工作流加进来之前的提交上（`git push` 先触发了旧的临时工作流），多花了一轮；做法上没错，但以后先把临时工作流和代码放进同一个提交再推分支。
- 这个 worktree 没有 `node_modules`，软链了主检出的；`pytest` 用的是主检出的 `.venv`（worktree 没有），和 8.29 记的做法一致。
