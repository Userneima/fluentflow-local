# 交付记录：长录像提取音频偏慢、原片旁字幕能不能只补转

2026-11-25 · 子对话（Claude，claude-opus-5-5）· 待办「效率」类「长录像：提取音频偏慢、原片旁已有字幕时能不能只补转（2026-10-27 实测）」

## 1. 改了什么

- **提取音频**（决策 4.23，提交 `1817b4d`）：这一步原来依次做三件事：抽转录用的 wav、编码播放用的 64k mp3、再整个读一遍 mp3 查是不是数字静音。现在 mp3 在这一步开始时起一个后台 ffmpeg，转录不等它，转录结束、结果写进任务前再等（`backend/core/audio_handler.py` 的 `CompressedMp3InBackground`）；任务失败或取消时在 `media_job` 的 `finally` 里停掉它。静音检查改读转录用的 wav（做了人声增强时读原片音轨，`require_audible_audio` 加了 `-vn`，不解码画面）。转录被打断后接着做：wav 照旧复用，mp3 没存下的在后台重编。mp3 格式、码率不变。原来的 `extract_compressed_mp3` 没有别的调用方，删掉了。
- **原片旁字幕只补转**（决策 4.24）：查后不做，理由见第 2 节。
- 测试：`tests/test_playback_audio_background.py`（6 条，按需求写：转录开始后才等 mp3、结束时停掉编码、后台编码出 mp3、ffmpeg 失败时报错、停得下来、静音检查不解码画面）。
- 文档：决策 4.23、4.24 和第四部分现状；更新记录一条；待办删掉这一节，「待补 Codex 审查」加一条，「agent 遇到的阻碍」加一条。

## 2. 怎么验证的

- 检查：`pytest -n 4` 2504 过、3 跳过；`ruff check backend/ scripts/` 通过；`git diff --check` 通过。没碰前端。
- 根因：10-27 那次任务的事件记录里 `audio_extracted` 437 秒，`stt_audio_take: plain`，没开人声增强、没剪气口，所以就是上面三件事。在复制到临时目录的整片（3:20:15，1.5GB，48kHz 双声道 AAC）上逐项测：wav 18–22 秒，mp3 78–116 秒（LAME 单核），读 mp3 查静音 11–12 秒，读 wav 只要 1.7 秒。
- 前后对比（同一份整片副本、同一脚本交替跑两轮，机器上同时有别的对话，负载 6 到 18）：

| | 第一轮 | 第二轮 |
|---|---|---|
| 改前：从开始到能转录 | 95.1 秒 | 132.7 秒 |
| 改后：从开始到能转录 | 18.3 秒 | 18.2 秒 |
| 改后：后台 mp3 编完 | 78.3 秒 | 85.4 秒 |

- 转录会不会被后台 mp3 拖慢：10 分钟片段，单独转 55.1、56.9 秒；旁边一直编着整片 mp3 时 58.6、56.3 秒，在波动范围内。
- 完整流程：`prepare_test_copy.py --fake` 的副本在 8013 起服务，5 分钟片段按 agent 提交（`cut=false`）：提取音频 0.5 秒，任务完成，`playback_audio` 生成（2.4MB），`/jobs/{id}/artifacts/playback_audio` 返回 200 audio/mpeg。
- ffmpeg 加了 `-v error` 后 30 分钟片段的 stderr 是 0 字节，后台进程的输出管道不会写满卡住。
- 字幕：和这次转录稿对照 10、50、90、130、160 分钟各 2 分钟，去标点相似度 0.79–0.93，互有对错；字幕到 3:00:40 结束，之后 20 分钟平均音量 -46 分贝（讲课 -16），截帧是直播结束后主讲人离开话筒看手机，转录稿 3:01:43 后一句没有；字幕每条中位 2.5 秒、87 条超过 10 秒（转录 2.0 秒、9 条）；张和训练营 6 条录像只有这一条带字幕。

## 3. 没做的、没验证的

- 10-27 那次为什么比现在慢 3 倍没法确认：同版本前一条 1 小时 51 分的录像只用 44 秒，最可能是当时机器被别的活占满，但服务日志不带时间，查不到当时在跑什么（已记进待办「agent 遇到的阻碍」）。
- 没在整片上跑完整任务：要转近 30 分钟，提取那一步的前后对比已经在整片上单独测过，完整流程用 5 分钟片段验证。
- 取消正在转录的任务时停掉后台 mp3，只有单元测试，没在服务上实测：5 分钟片段的 mp3 三秒就编完，来不及取消。
- Windows 和没有显卡的机器上没测转录会不会被后台 mp3 拖慢：那里转录跑在 CPU 上，会让出一个核约一分半钟。
- 实测过程记录没放主检出的 `private/测试记录/`：简报要求不动主检出，数字都写进了决策 4.23、4.24 和本文件。
- Codex 推送前审查没跑（额度用完），已在待办「待补 Codex 审查」记一条。

## 4. 这次得出的经验

- 慢的步骤先拆成每一遍读片各测一次，再和同一版本别的任务比速率，分清是做法慢还是当时机器忙。落点：决策 4.23 正文（项目内）。
- 待办写的前提要先核实：「字幕比原片短 20 分钟，直接用会漏内容」，查下来缺的是直播结束后的空白，没漏内容。动手设计前先查前提是否成立。落点：跨项目。
- 服务日志不带时间，事后查不出当时机器多忙。落点：待办「agent 遇到的阻碍」（项目内）。
