10. 240 字预览覆盖笔记的事故（`2260470`）：
    - 触发路径：从处理记录打开任务时，编辑页先拿到列表里那一份，笔记只有前 240 字、没有版本号，被当成整篇、可以编辑的笔记显示出来，直到页面自己读完整篇（当天那条要十几秒）。这段时间里笔记被改动一下，页面就认为有没保存的修改，到了的全文不再替换，随后把这 240 字不带版本号存回去，服务照单全收。用 22:03 时实际在跑的构建 `bdd21c9` 重放核实过，写请求全部拦下。
    - 新旧两个构建在重放里都不会自己保存，出事那几次保存是那段时间里有人或自动化页面改了笔记。第一次保存前有一次跨端口预检请求，所以多半来自另一个端口上的开发预览页面，不是 8000 上的网页。
    - 修法：页面打开任务时都向服务读一次这个任务，读到之前笔记栏只写「正在读取笔记全文…」；读到后连版本号一起换上；保存笔记一定带版本号。
    - `5fb9508` 和 `77644c2` 都没有新开这条路：从网址打开时先读全文再显示，提速只动了转录栏。

- 只关 FluentFlow：播放器该放哪个文件，必须跟着「转录用的是哪个文件」走，选择结果要作为重新载入媒体的依据之一。已写进 `docs/02-决策记录.md` 6.22。
- 只关 FluentFlow：转录原文提速的实测数字，以及 C、D 为什么不做，已写进 `docs/02-决策记录.md` 6.26；测试记录在 `~/Downloads/FluentFlow测试记录/2026-10-22-225330-编辑页转录原文速度/`。
- 只关 FluentFlow：编辑页拿到全文之前笔记不可编辑，保存一定带版本号；列表行和浏览器缓存里的笔记都截到 240 字。已写进 `docs/02-决策记录.md` 6.27。
- 只关 FluentFlow：剪过的录像里句子之间几乎没有停顿（量了四条），转录稿要分段只能按说话人和长度分。写在样机分支 `206ebfb` 的代码注释里，合进 main 时要写进决策记录。
- 跨项目：测试里替代数据请求的假对象，要和真的一样在整页只创建一次。每次渲染都给一个新对象，依赖它的副作用会反复执行，页面不停重画，测试卡死不报错。这次两个测试文件都踩了，查了一阵才发现是测试自己的问题。
- 跨项目：截短的预览不要用和全文同一个字段名。列表行里的 `summary_markdown` 其实只有前 240 字，编辑页就把它当了全文。
- 跨项目：页面上能编辑并会自动保存的内容，要先拿到服务端的完整版本再放开编辑；保存时带上版本号，没有版本号就不保存。
- 跨项目：量前端速度用正式构建，并且在前台的无头浏览器里量。开发版里的按键时间大约是正式构建的 2.5 倍（多出来的主要是 React 开发模式的检查）；隐藏的浏览器面板会被限速，量不准。量的时候把所有写请求拦掉，就可以在真实数据上放心地打字、播放。
- 跨项目：rebase 冲突用脚本解决时，脚本和 `git rebase --continue` 不要用 `;` 连在一起。这次脚本出错退出了，rebase 照样继续，把冲突标记提交进去了，在推送前发现后改掉。
- 跨项目：用派生出来的字符串作为副作用的依赖时，影响结果的每个输入都要算进去。这次播放器的依赖里没有「该放哪个文件」，记录补全之后就没有换文件。
