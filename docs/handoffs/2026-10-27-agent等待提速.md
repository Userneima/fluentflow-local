# 交接：agent 处理长录像时让等待几乎不花额度、导出时就能开始写笔记

2026-10-27 · 从「产品架构优化方向」主对话交接（那个对话已经太长，每一轮都要重读整段历史，换新对话本身就是为了省 token）

## 目标和完成标准

做 `docs/01-待办.md`「效率」一节第一条「agent 处理长录像：时间和额度大多花在『等』上」里的第 1、2 项。第 3 项（提取音频偏慢、复用已有字幕）不在这次范围，留在待办。

1. **等待几乎不花额度**：`wait_task` 能一次等很久（比如最多 10 分钟）；任务完成，或者需要 agent 出手（判断剪辑、写笔记）时，立刻返回。`agent/skills/fluentflow/SKILL.md` 写明：提交之后不播报进度，需要出手时再开口；派子助手写笔记时，不让它继承整段对话的上下文。
2. **导出剪后视频的同时就能开始写笔记**：agent 取写笔记的材料，不用等剪后视频导出完。参照 FluentFlow 自己写笔记那条路的做法：剪哪里一定下来，就按「原片当成剪后」给材料。

完成标准：
- 测试按需求写：长等待在状态变化时立刻返回，到上限时返回现状；剪辑定下后、导出完之前，agent 就能取到笔记材料，而且材料是剪后的时间轴。
- 在测试副本上用假模型实测一次：用 `scripts/prepare_test_copy.py --fake` 准备副本，再用 Codex 或一段脚本模拟 agent 走一遍。记下等待期间 agent 一共来回了几次，跟这次实测的 157 轮对比。
- 整套检查通过（照 `AGENTS.md` 的 Validation 一节）；已合进 main 并推送；满足重启条件时 8000 重启到新代码。
- 待办、决策记录、更新记录、`SKILL.md`、MCP 工具说明、维护手册都改成现在的样子。
