# 任务卡

一件事开工前写的一张卡：做什么、改到哪、怎么算做完、哪些不能碰。做完在卡上回填结果，攒一批再翻流程账本。

没有卡的时候，范围和验收只存在于这次对话里；换一个 session 或换一个人，就得靠猜。

## 什么时候开卡

按三条判，满足一条就开：

- **不止一个执行者**：会跨 session、跨 agent，或者你会走开再回来。
- **会并行**：和其他改动同时进行，或者两处改动之间有先后依赖。
- **错了不会当场暴露**：要等合并、等上线、等用户用才发现。

三条都不满足就不开，直接做。经验值：写卡加验收十来分钟，预计半小时内做完、返工也很便宜的，不值当。

## 卡里写什么

文件名 `docs/任务卡/<日期>-<短名>.md`，做完留在原处，不归档。

```markdown
# <一句话：这次做什么>

- 范围：改哪几个文件、哪一块；明确这次不做什么
- 对外接口：页面、agent、脚本会看到什么变化
- 验收命令：跑什么、看到什么算过
- 不能碰：这次不动的文件或行为
- 依赖：等谁、等哪个改动先合
- 谁审：默认一个新会话审，不看聊天记录
```

卡写不好比没有卡更糟：写得含糊，子 agent 会自己补，补出来的东西合起来对不上。标准是别人拿这张卡能不能独立做完。

## 做完回填

在卡末尾加一节「结果」，四个数：

- 用了几个 session
- 被打回几次（审查要求改的次数）
- 合并后又修了什么
- 卡本身要改的地方（一句话：哪个字段没写清，导致哪次返工）

这四个数不是给自己看的，是给流程账本用的。不填就等于没跑过，下个月没法判断这条规矩有没有用。

## 审查怎么用卡

审查的会话只拿三样：卡、diff、验收命令的输出。不看聊天记录，只报能复现的问题。卡里没说清导致的分歧，记在「结果」里，不要当场改卡。

## 流程账本

`docs/任务卡/流程账本.md` 记每条流程规矩有没有真拦住东西，规则和阈值在它的开头。
