- 谁来写：

  - 一个 Key 都没有：笔记记为跳过（`no_model_key`），不记为失败（5.23）；页面给一段可复制的话，发给用户自己的 agent 去写（5.27、5.28）。选了「只要转录」的不写。

- 写法只有一份，三条路（Claude、agent、文字模型）都读：用户自己的笔记 skill 存在就用它，否则用自带的 `fluentflow-note-default`；文字模型另加一段「这次只有转录文字」（6.64）。默认写法的更新不进用户的副本（5.31）。个人写法由 agent 提议、用户确认后写入，设置页只查看和撤回（5.38）；依据是他在对话里指出的错漏，和他点「学完了」时留下的改动记录，同一类写法问题出现两次才提议（5.59）。
- 系列校正文档 `FluentFlow 校正文档.md`：从录像所在文件夹逐层往上找，交给所有写笔记的路，按它写对（5.29）；进词表的规则见 5.36。
- 默认写法的要点：
  - 正文完全按录像里讲的先后写，不按主题重组（6.72）；标题下先写这一课教了什么、有步骤就列出来（5.45）。
  - 讲者的判断连理由一起写，现场问答写出问和答，不加笔记自己的评语（5.54）。
  - 拿不准的词照原样写、就地标「（存疑）」，不设末尾「存疑」一节（5.5）。
  - 术语原词照写、括号里附一句白话解释；英文缩写和行业说法第一次出现都解释；一段难懂概念多时在段首先交代（5.33、5.35）。
  - 会议按议题先后写、用名字称呼，结尾「决定」「待办」表格「还没定的」（5.18、5.30）；课程结尾一节回顾。
- 截图：在画面变化处抽帧，至少隔 2 秒、最多 120 张，去掉空白帧。订阅通道和 agent 拿全部，Key 通道在全片均匀挑 20 张。只放正文说不清、看图才明白的，可用 `#crop=` 裁出一块（5.6）。
- 长录像：
  - Claude 每段最多 6 万字、配自己的截图，后段沿用前段认出的人名和称呼（5.32）。
  - 文字模型两万字以内整篇写，更长的按章写，最后统稿时补标题、开头和结尾几节（6.64）。
  - 写的过程在编辑页和处理记录显示真实进度和已写好的内容（5.58）。
- agent 写笔记：
  - 默认一次取完整段材料、一次写完，交给不继承对话的新子助手（5.19、5.42）。
  - 收不下（Codex 上第一次就这样）带 `small_parts=true`：每段 7 千字，写法单独取一次（`instructions_only=true`）（5.48）；每部分交给一个新子助手，写一段存一段，存齐才替换任务的笔记（5.8、5.54）；最后通读一遍，补一级标题和开头（5.42、5.52）。某部分笔记短于那段讲话的 35% 时提醒再查一次（5.54）。

  - 剪辑一定、导出期间就能取材料开写（5.41）；转录稿修正还留给 agent 时，先修正再写笔记（5.49）。

### 5.5 拿不准的词就地标「（存疑）」

2026-10-14 · 王愉超定

- 问题：默认笔记写法把靠猜的人名、产品名、数字统一放到笔记末尾的「存疑」一节。长笔记读到末尾时，已经忘了这些点在前面哪里提到。而且这条有时没守住：同一份笔记把「这个你给我们拉模拟做的差不多了」写成了「他提到相关模拟已经基本做完」，「拉模拟」读不通，大概率是语音识别听错的工具名。
- 考虑过：正文写「（转录读不清，见存疑）」再在末尾列原话和可能的意思（我原本这样提的）。
- 决定：拿不准的词照转录稿原样写，后面直接加「（存疑）」，不再有末尾的「存疑」一节。查漏补写时已标的词和标记原样保留，不改成猜的写法。
- 长录像拼接时仍会把各部分的「存疑」一节收到末尾：用户自己的写法是从旧默认写法复制的，还会要求这一节，不收就会在每部分中间各留一节。默认写法不再产生这一节，这段代码对它不起作用。
- 依据：同一场周二会议（14 分钟），新旧写法各写一次。旧写法有末尾「存疑」一节，并把「拉模拟」改写成「负责的人说模拟已经做得差不多了」；新写法正文里标了 7 处「（存疑）」，「拉模拟（存疑）」原样保留，没有末尾一节。旧写法在末尾那一节里写的推测（「诚哥」可能是钟艺诚），新写法不再写。每版只写了一次。

### 5.6 笔记里的截图只放值得看的，并裁到有用的一块

2026-10-14 · 王愉超定

- 问题：录屏和会议抽出来的帧是整个桌面。Claude 按「这一刻屏幕上是表格」去引用，不判断截出来能不能看清。冲刺规划会那份笔记放了 4 张整屏截图：表格那张字读不出、还被 Notion 弹窗挡住；Slack 那张要说的事正文已经写了。
- 考虑过：一律不放截图（截图只给 Claude 读画面用，录音转笔记 skill 原本就是这么定的）。王愉超要的是能判断的就判断：有用的留、裁掉无用的部分。
- 决定：正文说不清、看图才明白的才放；正文已写清的、裁出来仍读不清的、缺了关键信息的（例如表格少了任务名那一列）不放。放的图裁到共享的页面或窗口里有用的一块，小图按原大小显示，放在它说明的那段旁边，图下一行图注写「看这张图能看到什么」。
- 依据：手工复核那份笔记，4 张删 2 张，另 2 张裁剪后保留，PDF 从 2.5MB 降到 0.8MB。
- 做法（2026-10-14）：固定要求里加了裁剪写法，引用截图时在文件名后写 `#crop=x0,y0,x1,y1`（左上、右下两角的位置，按宽高的比例）。保存笔记时按原图分辨率裁出这一块，存成新图替换原引用；区域越界、太窄或几乎是整张图时，保留整张。裁出来的图和其他截图一样计入「引用了哪些截图」，导出 PDF、Word、Markdown、飞书和产出文件夹都用它；Word 里比页宽小的图按原大小放，不拉大。默认写法里加了「放之前先判断」「只要一块就裁」「图放在它说明的那段后面」。
- 写法改动还没有在真实录像上跑新旧对照，和待办第一批的对照实测一起做。

### 5.7 每份笔记写完逐条查漏

2026-10-12 至 13 · 王愉超定 · 提交 eebf4be、ec94dad、62029a2

- 目标：让「精讲笔记、知识点不漏」在每条写笔记的路上都成立，能拿来对外说。
- 原状：只有文字模型这条路、而且转录超过两万字时才查；「查到了」指的是知识点被分到了某一章，不是最终笔记里写了。Claude 看截图写的、agent 写的都不查。
- 决定：
  - 三条路共用一个查漏步骤，拿最终笔记对照原稿查。Claude 和文字模型写的漏了就补；agent 交回时照常保存，同时把漏项退回给它补。
  - 默认开，不给开关。
  - 界面不显示查漏结果：漏不漏是读者自己的判断，只记在任务数据里排查用。
  - 课程安排、考勤作业、闲聊、个人经历不算知识点；按这份笔记的写法判断算不算漏。
  - 补写时顺手把全篇理顺，只改说法，不改事实（他看了对比，觉得润色挺好）。
  - 只查一遍、补一遍，不追到底：不是所有细节都要保留。
- 依据：8 份已有 Claude 笔记（50 到 150 分钟）列出约 1100 个知识点，判为没写到的约 290 个，其中核心知识约 116 个、例子和数字约 116 个、课程安排和闲聊约 60 个。抽查大多是真漏，也有误报。同一份笔记查两次，列出的知识点不完全一样，所以对外只能说「逐条核对、漏的会补」，不能说「不漏」。一节 55 分钟的课补写后，盲评认为新版更好读，事实和数字没被改动。
- 后续：张和训练营的视频由他对照着看，按实际结果再调。

### 5.8 agent 写笔记做成主路：小段、写一段存一段、最后通读

2026-10-14 · 王愉超定

- 判断：没有 Key 时，笔记交给用户自己的 agent 在对话里写，是正道。它不靠 Claude Code，Codex 这类能接 MCP 工具的 agent 都能用，用的是用户已经付费的订阅。借用户的 Claude Code 订阅登录、由 FluentFlow 在后台自己调 Claude，Anthropic 是否允许还没核实，而且只对装了 Claude Code 的人有用。
- 问题：给 agent 的材料按 6 万字一段，跟 FluentFlow 自己调 Claude 时一样。实测百校第 1 段约 6.6 万字符，Claude Code 一次工具返回只收约 2.5 万 token，超出的被存成文件；改成让 agent 读文件也一样，读文件一次也只给 2.5 万 token，这一段要分三次读。中文约一个字一个 token（这一段 6 万字是 54,766 个 token）。
- 决定：
  - 给 agent 的材料按 1.5 万字一段切，连同写法要求和截图清单，每次取到的不超过 2.5 万字。百校切成 5 段，每段取到的约 1.9 万字。FluentFlow 自己调 Claude 的那条路仍按 6 万字一段，那条路一次请求装得下。
  - 写一段存一段。存过的部分放在任务的产出目录里，对话被压缩或换了新对话都能接着写；全部存齐才替换任务的笔记，原来的笔记照常可以恢复。转录改过的那一段，之前存的作废、要重写。
  - 存齐后让 agent 逐部分取回已存的笔记（不带转录，篇幅小）通读，合并几部分之间重复的结论和术语解释，改哪部分就重存哪部分。重存不改变「可以恢复的是 agent 动笔之前那一篇」。
  - 笔记拼好后如果又被改过（编辑器里的修改、别的写法重写），之前存的各部分作废，这次存的部分算新一轮的开始：各部分重新存齐之前不动现在的笔记，存齐后被替换的是改过的那一篇，可以恢复。整篇交回原来对分段的录像会被拒，现在接受。
  - 「可以恢复的」始终是 agent 第一次拼好之前那一篇，中间因为转录改过而重写了几部分也一样。（复查时发现：最初的做法在「改过笔记又改过转录」时会覆盖手改，在「改过转录后重新存齐」时会丢掉 agent 动笔前那一篇。）
- 2026-10-16 起默认改为一次取完、一次写完（5.19），分段只在 agent 收不下时用。

### 5.9 任务包不再附带转录全文和逐句分段

2026-10-14 · 王愉超定

- 问题：agent 读任务包（`get_task_package`）时，一条 2.5 小时录像的任务包约 52 万字，其中逐句分段两份共 45 万字、转录全文 4.3 万字、笔记 1.8 万字。Claude Code 一次工具返回只收约 2.5 万 token，所以几乎每条录像的任务包都被存成文件，agent 要分十几次读。
- 原因：第一版从托管版带来的设计，想让程序读一次就拿到任务的一切；给程序调 HTTP 接口用没问题，包成 agent 的工具后才撞上限。随产品的 agent skill 没有一处用到转录全文或逐句分段，写笔记用的转录走取材料的工具。
- 决定：转录只给有没有、多少字、开头预览和文件位置；笔记全文保留。任务包版本从 1 升到 2。改完百校那条约 3 万字，其中笔记 1.8 万字。
- 考虑过：笔记按节读、按节改。按节读解决的长笔记现在少见，很多修改（全篇啰嗦、跨节重复、到处都错的人名）也要看全篇；它真正的好处是只交回改过的部分，记进待办，等有了 agent 实际修笔记的记录再定做法。

### 5.10 验证规则时重写的那一段，和 agent 取材料是同一段

2026-10-14 · 托管版遗留问题清理

- 问题：给 agent 的材料改成 1.5 万字一段后，「按候选规则重写一段」（`draft_note_part`）还按 6 万字切。agent 说「第 3 部分」时，两边指的不是同一段录像，段号还可能超出范围；记录反馈时冻结的转录片段用的是 agent 的切法，也对不上。

### 5.13 查漏的每个请求最多等 10 分钟

2026-10-15

- 问题：运营会议（38 分钟）的笔记写完后停在「查漏」一个半小时。查漏请求发给设置里的文字模型（DeepSeek），连接一直开着，却没有答完；进程里没有别的在跑，日志也没有报错。
- 原因：客户端的超时只管"两段数据之间最多隔多久"，不管"整个请求最多多久"。服务商排队时每隔一会儿发一点空内容保持连接（DeepSeek 的非流式请求就这样），这个超时永远到不了。
- 决定：每个查漏请求从发出到答完最多 10 分钟，超时就当这次查漏没跑成，笔记照原样保存，任务里记下查漏没完成。正常的查漏一两分钟答完。
- 被卡住的那次只能靠重启服务解开（Python 打断不了一个阻塞着的网络读取），重启后重写那条笔记。

### 5.14 写完笔记不再加一轮核对

2026-10-15 · 王愉超定

- 原计划：让 Claude 按写法文件里能逐条判断的硬规定再查一遍并修改，先做实验比较效果和费用。
- 决定：不做。每份笔记已经逐条查漏（5.7），再加一轮核对每篇都多花一次模型调用和几分钟，能多抓到的问题很可能和查漏重叠，投产比太低。

### 5.16 新剪辑流程下，文字模型的笔记也在剪完之后写

2026-10-16 · 只读审查发现，按待办修

### 5.17 agent 等任务时，等到剪辑和笔记都完成

2026-10-16 · 看 Codex 那次实测发现

- 问题：任务存好转录稿就显示「已完成」，之后才剪辑、写笔记。等待工具原来靠「任务最近有没有变化」判断笔记是不是快开始了，导出剪后视频时两分钟以上不更新任务，它就会回答「完成」，这时还没有笔记。张和 2 号那次导出刚过两分钟，长录像会差好几分钟。
- 决定：剪辑在进行时，等待工具和查任务一律回答没完成，并多给一项「正在剪」。MCP 工具说明改成现在的流程：先转录原片、模型读完决定剪哪里、再写笔记；并写明 agent 想用自己的订阅写笔记的做法（提交时只要转录，再取材料、存笔记）。


### 5.18 会议录像按会议写：决定和待办放在结尾，参会的人用名字

2026-10-16 · 按 5.15 做

- 现状：默认写法按录像内容自己选结构，会议录像已经按议题写，但三处像学习笔记：结尾是「定义、机制、边界」式的回顾；分工散在各节，没有一处能一眼看到谁做什么；参会的人统称「讲者」。
- 决定：不另加一步判断录像类型，写笔记的模型读材料时自己判断是不是会议。是会议就按议题写清讨论、看法、结论；结尾一节「决定」、一节「待办」表格（事项、负责人、截止时间、备注），负责人和截止时间取会上说的和画面上的，两处都没有写「未定」；称呼用会上的名字。课程和讲座照旧。文字模型的提示词加了同样一条。
- 实测（Claude 订阅，新旧写法各写一遍）：两条会议录像（布置任务的周会、运营会）新写法都有决定和待办，「讲者」从 11 次、2 次变成 0 次，负责人名字取自会议画面上的参会人名单；一条讲座录像结构不变，没有多出会议的节。对比稿存在本机 `private/测试记录/2026-10-16-会议笔记写法对比/`（公司会议内容，不进仓库）。「画面上的截止日期也算」这一句是看完对比后加的，没再跑一遍；文字模型那条没实测，这台机器的文字模型 Key 在网页设置里，命令行取不到。


### 5.19 agent 写笔记默认一次取完、一次写完，交给子助手

2026-10-16 · 王愉超定

- 问题：5.8 按 1.5 万字一段把材料切给 agent，因为 Claude Code 一次工具返回超过上限就存成文件。王愉超指出一篇笔记对 agent 没有难度，分段写还要最后通读去重；写到一半被压缩，开个新对话（子助手）就能避开。
- 实测：Claude Code 的上限调 `MAX_MCP_OUTPUT_TOKENS` 没用，超过 5 万字符的结果照样存成文件。工具自己声明 `_meta["anthropic/maxResultSizeChars"]`（最多 50 万字符）才行；声明后 2.6 小时录像的全部材料（约 13 万字符）一次直接收到，用户不用改任何设置。
- 决定：
  - 取材料默认给整段转录；agent 收不下（被截断、存成文件）时带 `small_parts=true` 再取，退回 5.8 的分段写法。
  - 写笔记交给子助手：它从空白上下文开始，取材料、写整篇、存一次，主对话不装转录稿。
  - agent 整篇存好几次（补查漏、改错）时，可以恢复的仍是它动笔之前那一篇。实测时发现存三次后恢复回来的是 agent 自己的第二稿，已修。
- 实测（Claude Code 订阅，子助手写）：张和 kickoff 58 分钟（剪后约 32 分钟）一次取完，写 8900 字，存 3 次，约 15 分钟；2.6 小时的答疑录像一次取完，写 1.9 万字，存 2 次，约 13 分钟，没碰到输出长度上限。每存一次 FluentFlow 都用 Claude 查一次漏，抽出的知识点每次不一样（同一篇 60、84、73 个），所以说明里只让 agent 补一次。测完两个任务的笔记已换回原来那篇，agent 写的稿存在本机 `private/测试记录/2026-10-16-agent一次写完整篇/`。

### 5.20 agent 写的笔记只在第一次存时查漏

2026-10-16 · 王愉超定

- 问题：agent 每存一次 FluentFlow 都查一次漏。查漏每次挑的知识点不一样（同一篇 60、84、73 个），所以补完再存又报新的漏项，补不完，每次还多一次模型调用和几分钟。
- 看了实测剩下的漏项：大多是学员项目的演示步骤、讲者顺口的评价和原话，少数是该写的理由和前提，有一条误报。有价值的是第一轮：2.6 小时那条第一轮查出 45 处，补完笔记多了约 3300 字。
- 决定：每篇笔记（分段时每一段）只在第一次存时查，agent 把值得写的补进去再存一次，这次不再查。和 5.7「只查一遍、补一遍」一致。

### 5.23 一个模型 Key 都没有时，笔记记为跳过，不记为失败

### 5.24 文字模型的默认放进一张能远程更新的推荐表

### 5.25 Claude 报认证失败时先确认是不是真没登录

### 5.27 用户订阅写笔记的路：一段发给 agent 的话，不是后台调用

2026-10-18 · 王愉超定

- 问题：用户希望默认用自己的订阅写笔记，包括换成 Codex、WorkBuddy 的人。FluentFlow 在后台自己调用用户的 Claude 登录（`claude -p`）明确不符合 Anthropic 的规定：第三方产品不能向用户提供 claude.ai 登录或订阅额度。
- 决定：后台调用订阅的通道只给开发者自己用，仍然只在 `.env` 里设 `FLUENTFLOW_VISUAL_NOTE_CHANNEL=subscription` 才打开，设置页不出现。给用户的路是一段话：笔记栏没有笔记、或笔记是文本模型代写时，页面给出一段可以复制的话，发给用户自己的 agent（Claude Code、Codex、WorkBuddy 等），由它通过 MCP 取材料、写笔记、存回去，用的是它自己的订阅。这段话不管 agent 有没有接入过都能用：里面写着本机 FluentFlow 的 MCP 服务怎么接（Python 路径和脚本路径，取自运行中的服务），不带令牌，服务自己从 `.env` 读。
- 网页不会主动把提示发给 agent：agent 不接收外来的消息，MCP 只能由 agent 来调；由 FluentFlow 启动 agent 的命令行又回到了上面那条不允许的路。

### 5.28 写笔记的模型加上 Kimi、MiMo，首推通义千问，再之前是自己的 agent

2026-10-18 · 王愉超定

- 问题：首页「让它帮你写笔记」只给 DeepSeek 和 Anthropic 两个选项，Anthropic 的 Key 国内用户一般申请不到；Kimi、MiMo 只能填在「看图模型」里判断剪辑，不能写笔记。
- 决定：首页卡片先推荐交给自己的 agent 写（给一段能直接发给 agent 的话，见 5.27），下面才是填 Key 让 FluentFlow 自己写。Key 的选项按通义千问（推荐）、DeepSeek、Kimi、MiMo 排，只有这个版本自己结合画面写笔记时才列 Anthropic，并注明国内账号一般较难申请。设置页的服务商下拉也是这个顺序。
- 做法：写笔记的服务商收成一张表（后端 `text_providers.py`、前端 `textProviders.js`），地址、Key 字段、环境变量、默认模型、模型列表的过滤都在表里，各处从表里读；加一家就是加一行。Kimi 用月之暗面国内平台 `https://api.moonshot.cn/v1`，默认 `kimi-k2.6`；MiMo 用小米官方 `https://api.xiaomimimo.com/v1`，默认 `mimo-v2.6-pro`（官方文档 2026-10-18：V2.5 系列 10 月 21 日下线）。两家的默认也写进推荐模型表，以后换名不用发版。地址可以用 `KIMI_BASE_URL`、`MIMO_BASE_URL` 改（比如 Kimi 的国际平台）。
- 没有 Key 时谁先用：顺序还是 DeepSeek、OpenAI、通义千问，后面接 Kimi、MiMo，已经填了 Key 的人不会因为多填一家就换了写笔记的模型。
- 没实测：这台电脑没有 Kimi、MiMo 的 Key，两家只按官方文档接上，Key 校验和模型列表用的是各家的 `/models`。

### 5.29 系列文件夹里的校正文档

### 5.40 agent 等任务时一次最多等 4 分钟，需要它出手时立刻返回，中间不播报

### 5.41 agent 写笔记不等剪后视频导出完

2026-10-27 · 按待办「效率」第一条做

- 问题：agent 交回剪辑决定后，要等剪后视频导出完（那条 3 小时 20 分的录像导出 15 分钟）才能取写笔记的材料。挡住它的是取材料接口的「队列忙就拒绝」：导出时这条任务自己占着队列，接口回「有任务正在处理中」。FluentFlow 自己写笔记那条路早就是剪哪里一定下来就开始写（批次三，2026-10-16）。
- 决定：照 FluentFlow 自己那条路做。剪辑决定在导出前就存在任务上（原来只存剪哪几段，现在连留下的几段一起存），导出期间 agent 取材料时，转录稿按留下的几段换算到剪后视频的时间轴，截图从原片上剪后会出现的时刻截取；导出完以后取到的转录稿和截图跟导出期间一字不差，分段存的部分照样有效（有测试核对这一点）。导出期间不再因为队列忙而拒绝这条任务自己的取材料。`wait_task` 在剪辑定下、开始导出时返回一次「可以开始写笔记」，只说一次：子助手还没开始取材料、或取材料失败时，后面的等待也不再为它立刻返回。导出期间存下的笔记照常成为任务的笔记；导出随后失败时，笔记里的时间和截图换回原片的时间轴，和 FluentFlow 自己那条路一样。导出已经失败或被停下之后才交回的、按剪后时间写的笔记，存的时候拒绝，告诉 agent 重新取按原片的材料再改。
- 存在任务上的剪辑决定记着它属于哪一次导出：导出失败后留下的决定要留给重启接着导出用，但之后改判剪辑、手动重剪这类不重新判断的导出，不会被当成这个决定来给材料。
- 剪辑还在判断、没定下来时，取材料明确拒绝并说明原因。原来这时如果队列正好空着，会按「只有转录稿」写，用的是原片时间轴，和后面的剪后视频对不上。

- 交给 agent 的任务（转录稿修正留给 agent 时）不再提前开始写笔记，见 5.49。

### 5.42 读录像的活默认交给新子助手，主对话只提交、等待、交付

2026-10-28 · 复盘 2026-10-27「Agent时代的评测体系」那次 Codex 实测（`private/测试记录/2026-10-27-Agent评测视频处理复盘/`）

- 问题：子助手写前 3 部分笔记共约 6 分钟；它因额度用完停下后，续接的主对话自己补写后 2 部分、通读、对齐 83 节，用了近 2 小时，每次操作间隔 2 到 7 分钟。主对话里早已装着剪辑材料（约 9 万字时间线和 24 张截图）和几十次等待，每一轮都要重读这些。另有两处返工：通读改完一处，回答又要求整篇通读一遍；对齐材料取到一半又改了正文，材料过期重取。
- 决定：剪辑判断、写笔记、续写没写完的部分、通读、对齐，默认都交给不继承对话的新子助手（宿主有子助手时）。说法放在 agent 当场看得到的地方，不只写在 skill 里：等待返回「要你判断剪辑」时、剪辑材料工具的说明里都写明交给子助手。笔记分段写到一半停下的，`get_task` 的 `note_draft` 和 `wait_task` 做完的回答列出还差哪几部分，让新子助手只写这几部分，不让主对话自己取材料。
- 一篇笔记只通读一遍：拼成全文时要求通读；通读中改存某一部分，回答只说「还有要改的照样存，改完就结束」，不再要求再通读。拼成全文时提醒对齐的那句改成「不再有部分改动之后再对齐」。
- 额度用完造成的停顿（那次约 4 小时）不在 FluentFlow 能管的范围：主对话和子助手用同一份额度，多开子助手兜不住。上面这些让每一轮读的东西变少，额度烧得慢一些。省多少没有实测，按子助手的速度推算续接后能少一小时以上。

### 5.45 笔记开头写这一课教了什么，不写录像是什么场合

- 只改措辞、只影响开头一段，按 8.8 属于小改动；还没在真实录像上跑新旧开头并排对照。只影响以后写的笔记，已有笔记不重写。

### 5.46 慢工具每 4 分钟先回一次「还在做」，再调一次接着等同一次运行

2026-11-05 · 按待办「效率」里的 Codex 超时一条做；王愉超说产品用户主要用 Codex

- 问题：Codex 一次工具调用最多等 300 秒（5.40 的实测）。写复习笔记最多要 45 分钟，改复习笔记、按词表修正、委托模型查漏、试写一部分笔记也都可能超过 5 分钟。在 Codex 上这些调用会先被判超时，FluentFlow 那边照样在做，agent 却以为失败了，可能再调一次、多花一次模型额度。
- 两条路：安装时替用户在 Codex 的配置里调大 `tool_timeout_sec`，或者让工具自己在 Codex 放弃之前回话。5.40 定过不改用户的 Codex 设置，而且调大配置只对 Codex 有用，所以选后一条。
- 决定：这五个工具（`write_review_note`、`revise_review_note`、`run_glossary_correction`、`draft_note_part`、带 `model_check=true` 的 `save_agent_note`）在 FluentFlow 的 MCP 进程里另起一个线程去做，最多等 240 秒；没做完就回 `still_working`，说明没出错、照原样再调一次。参数完全相同的再次调用接着等同一次运行，后台只被请求一次；参数不同算另一次。结果交回一次后就清掉，之后再要同样的东西会重新做；做完了 30 分钟没人来取的也清掉。对话结束时 MCP 进程退出，等待随之结束，后台那边的活照常做完。
- 不改后台接口，Claude Code 也走同一条路（每 4 分钟多一轮调用）。MCP 进程中途重启时，再调一次会重新请求后台：复习笔记和词表修正后台本来就会以 `already_running` 拒绝重复的那次，另外两个会重做一次。
- 用替身后台测过「先回还在做、再调不重复请求、最后拿到结果」，还没在 Codex 上真跑一次写复习笔记。

### 5.47 复习笔记默认由当前 agent 写

2026-11-05 · 按待办「质量」第一条做；王愉超说产品用户主要用 Codex

- 问题：随看笔记、剪辑判断、修正转录稿都已默认由当前 agent 做（6.48、4.16），复习笔记还只能由 FluentFlow 自己的模型写：没登录 Claude 订阅、也没配 Key 的 Codex 用户写不了，配了的要另花一份额度。
- 决定：`write_review_note`、`revise_review_note` 默认由 agent 写（`writer` 默认 `agent`），`writer=fluentflow` 才用 FluentFlow 的模型。agent 拿到的材料就是模型拿到的那一份（写法、随看笔记、章节表、剪后视频转录稿；修改时是写法、用户意见和现在的复习笔记），按 1.5 万字一段分段给，Codex 一次显示得下（后改为 9 千字，见 5.48）。交回之后走和模型写的同一段代码：缺节拒绝、出处换成链接、写底稿版本、旧的一份存进历史版本、印 PDF、在任务上记下是谁写的（`agent:<模型>`）。仍是这两个工具加参数，不另开工具（工具说明的总长度只剩 2500 字余量，也照「只差一个参数的两个工具合成一个」）。
- 取材料到交回之间，用户在 Obsidian 里改了随看笔记或复习笔记，交回时拒绝（`stale`），让 agent 重新取材料：按旧材料写的笔记会把用户刚改的内容盖掉。判断依据是写法加材料整体的指纹，交回时重算一遍。
- 写法要求 agent 交给不继承对话的新子助手写（照 5.42）。
- 用替身测过：同一份回答，agent 交回和模型写出的文件逐字相同。还没让 Codex 在真实录像上写一份，和 FluentFlow 模型写的比质量。

### 5.48 在 Codex 上写笔记的分段改小，写法只给一次

2026-11-05 · 第四课交给 Codex 全程处理之前的审查

- 问题：`small_parts` 原来按 Claude Code 定的（每段 1.5 万字，Claude Code 一次能收约 2.5 万 token），在 Codex 上每段仍超出它显示的约 1 万 token；而且每段都带一份约 6 千字的写法（含用户自己的规则）。复习笔记的材料每段也是 1.5 万字。
- 决定：`small_parts` 每段降到 7 千字。用一条 2 小时的课实测（转录 7 万字、101 张截图）：7 千字一段，回答最长 11,461 字符；8 千字一段最长 13,199。写法放不进每一段，改成单独取一次（`instructions_only=true`，只给写法和交回方式，不带转录和截图，也不截图），每段只带这一段特有的说明，并写明写法在哪：交给子助手续写剩下几段时，子助手也能找到。不带 `small_parts` 时照旧一次给全部，写法在里面。复习笔记材料每段降到 9 千字，写法本来就只在第 1 段开头。
- skill 写明在 Codex 上第一次取材料就带 `small_parts=true`，先取一次写法。
- 没在 Codex 上真跑过；第四课是第一次。

### 5.49 交给 agent 的任务先修正转录稿，再写笔记

2026-11-05 · 第四课交给 Codex 全程处理之前的审查；部分取代 5.41

- 问题：交给 agent 的任务，按画面字幕修正、按词表修正都留给 agent（4.16、6.48），修正的材料要等任务做完才给（做的过程中拒绝）；5.41 却在剪后视频导出时就叫 agent 开写笔记。两条一起，每条交给 agent 的任务写出的笔记读的都是没修正的转录稿，听错的名字和术语进了笔记。
- 两条路：让修正也在导出期间做（要改修正材料「任务做完才给」的前提，剪后时间轴换算也要跟着改），或者让笔记等修正。选后一条：质量排在省时间前面，代价是笔记要等导出完、修正完才开始写，三小时的录像多等十几分钟导出。
- 决定：转录稿修正还留给 agent、没做完时，`wait_task` 不再在导出时说「可以开始写笔记」。任务做完时，`wait_task` 的 `next` 按顺序只给一步：没写完的笔记接着写 → 修正转录稿 → 写笔记 → 对齐章节时间；交回最后一页修正时，回答的 `next` 说接着写笔记。笔记已经写过的任务不再提示写笔记。配英文字幕的翻译不挡笔记：笔记不读它。
- 用替身测过这三处的顺序和提示。

### 5.50 一次等待至少 4 分钟，agent 填的更短也照 4 分钟

2026-11-05 · 第四课 Codex 全程实测；王愉超同意

- 问题：`wait_task` 默认一次等 240 秒，Codex 却每次自己填 55 秒。等待期间每回来一次，Codex 就要重发整段对话再调一次，三小时的课转录、导出几十分钟，次数多出三四倍。
- 决定：MCP 端把小于 240 秒的等待时长按 240 秒算，上限仍是 600 秒。有事要 agent 做时本来就立即返回，等得长不耽误。240 秒在 Codex 单次调用的 300 秒以内。
- 更进一步是让一次等待一直等到有事或做完：要 Codex 给 FluentFlow 的工具调高单次等待上限（`tool_timeout_sec`）。之前定过不替用户改 Codex 配置，先在王愉超的 Codex 上实测它是否生效，生效再写进安装说明由用户自己决定。

### 5.53 笔记拼好以后再改转录稿的词，按部分存的笔记照样能按部分改

  - 主因是写的方式：实跑时一个子助手在 5 分多钟里连写 12 部分，每部分笔记只有那段讲话的 18% 到 26%。同样四部分每部分单独开一次 Codex 写，旧写法就有 51% 到 67%，理由覆盖 93%（原版这四部分 67%）。
  - 写法文字也有影响：评语来自「准确」一节（只写能确认的、分清讲者观点和推论），Codex 把它读成要给每个判断加免责的话。
- 决定：
  - 默认笔记写法（`fluentflow-note-default`，Claude 和 agent 都读这份）：「不漏」里加两条，讲者下判断、给建议、做取舍时判断和理由一起写，压缩时删重复不删理由；现场问答写出问了什么、答了什么。查漏那条点明要对到每个判断的理由和每组问答。「准确」里加一条：讲者说是推测或个人体感的，先写推测的内容和理由，再照他的原话标明，不另加笔记自己的评语。
  - Codex 分段写（`small_parts`）时，每一部分交给一个新开的、不带前面对话的子助手，写完存好就结束，最后再开一个做通读（agent skill 和存部分后的回答都这么说）。没有子助手的宿主照旧自己接着写。
  - 存一部分时，笔记短于那段讲话（去掉时间）的 35%，照样存下，回答里多一个 `short`，请它对照这部分转录再查一遍理由和问答再存；每部分只提醒一次，再存的不论改没改都收下。长短不判断笔记好坏，只是请写的人自己再看一遍：数据上，单独写的部分在 51% 到 70%，连写漏理由的在 18% 到 30%，第三课 Claude 写的整篇是 49%。
- 实测（第四课全篇，Codex 在一个会话里连写 12 部分，按实跑的方式；没给截图）：

  | 版本 | 理由覆盖（核心） | 问答和例子（细节） | 评语 |
  | --- | --- | --- | --- |
  | 实跑原版 | 63% | 60% | 7 处 |
  | 旧写法 | 75% | 71% | 4 处 |
  | 新写法 | 82% | 80% | 0 处 |
  | 新写法 + 太短提醒 | 87% | 87% | 0 处 |

  评语按同一组说法数（「需实测」「待验证」「待核实」「不是已验证」「内部证据」「把推测当作」这类）。

  同样四部分（第 2、4、5、8 部分，核心 23 条）每部分单独写：原版 67%，旧写法 93%，新写法 96%。提醒在连写里只管用一次：第 5 部分被提醒后从 1093 字补到 1445 字，之后几部分 Codex 原样再存一次就过去了，所以主要靠每部分一个新上下文，提醒是兜底。每部分一个新上下文的做法用单独调用模拟，还没在 FluentFlow 的真实 Codex 流程里跑过；下一条 Codex 处理的录像是第一次。
- Claude 那条路没变差（2026-11-06 补跑，main `bfb8ded`，「合并文字模型和 Claude 两套写法」还没推上来）：原有的课程考题（kickoff）上，同一条录像按改前、改后写法各写一次，核心覆盖 99% 对 97%，细节 97% 对 95%，两版都没有错误、三个问题都答上；差 2 个百分点，在一条核心要点的浮动以内。第一次补跑时，改后那版本机 Claude 40 分钟没有返回、被中断；超时时命令行的输出被丢掉，查不出卡在哪。重跑时把输出逐行存下来，两版都在 8 分钟内正常写完，期间出现过订阅的限流事件。卡住的那次，同时还有三四个别的 Claude 订阅调用在跑，是不是被限流拖住没有证据。

### 5.56 在 Codex 上等待：脚本第一行写明一次等 300 秒

- 试过没留下的：把同一句话写进 `wait_task` 的工具说明、或在提交和等待的回答里加一句提醒（只对 Codex），Codex 都没照做，照旧每 20 秒回来；只有读了 skill 才照做。所以只改 skill。没读 skill 的 Codex 照旧多花，用户说「用 FluentFlow 处理」时 skill 会被触发（11-05、11-06 实跑都读了）。
- 实测（同一段 25 分钟片段的副本，假模型做剪辑和笔记，Codex 只提交、等完、报笔记位置；每次只跑一遍）：

  | | 等了多久 | Codex 请求次数 | 输入 token |
  | --- | --- | --- | --- |
  | 改前（没读 skill，和 11-06 读了旧 skill 的行为一样） | 12 分钟 | 37 | 168 万 |
  | 改后（读了 skill） | 16 分钟 | 10 | 45 万 |

  每分钟等待从约 13.6 万降到约 2.8 万，少约八成。改后那次等得更久，是因为同时还有别的测试在占机器转录。照这个比例估算，11-06 那次的等待（约 500 万）会在 100 万左右，没有重跑验证。

### 5.58 FluentFlow 自己写笔记时，页面显示真实进度和已写好的内容

2026-11-09 · 用户反馈：DeepSeek 写笔记时页面只有转圈和「正在写笔记」，一等几分钟 · Claude 实现，假模型副本实测

- 决定：写笔记的过程报告它实际知道的进度，编辑页笔记区和处理记录都显示出来，不写和进度无关的文案。
  - 文字模型（DeepSeek 等）长录像：「正在读转录稿、提取要点：已读 3/8 段」→「要点提好了，正在定章节」→ 列出各章标题，「已写好 2/5 章」→「统一全文的文风和编号」→「对照转录稿查漏」→「补漏」。短录像：「正在写笔记：已写 1234 字」。
  - 文字模型的正文改成流式返回，各章（短录像是整篇初稿）一边写一边显示在笔记区，标明是初稿、写完换成定稿。统一文风那一轮不流式显示：它从头重写整篇，显示出来像是写了又从头来。
  - Claude 看画面写：取画面、第几部分共几部分和这部分对应的时间段、已写好的部分（写好一部分显示一部分）、查漏。Claude 命令行这条路一次请求整段返回，拿不到逐字进度，单部分的录像只显示「Claude 正在结合画面和转录稿写笔记」和已用时间。
  - 已用时间都显示。剩余时间只在分部分写、且已写完至少一部分时，按这一次前几部分的平均用时估；其余情况没有可靠依据，不估。
- 怎么做：进度放在 `backend/core/note_progress.py`，只在内存里（服务重启后笔记从头写，旧进度没用）；`task_activity` 在笔记这一步进行时带上进度摘要，处理记录轮询时正在写的任务每次都发回；编辑页另走 `GET /jobs/{id}/note-progress` 取进度和已写好的正文，每 2.5 秒一次。流式只在写正文的请求上开（`note_progress.showing`），查漏、提要点这类请求照旧整段返回。服务商拒绝流式参数时（还没写出任何字）改用非流式重发一次，不会重复收费。流式回答没等到模型说「写完了」就断开，这一步记为失败（可以接着做），不把半篇当成整篇存下。
- 顺带修的：从转录稿文件写笔记时，编辑页原来不轮询这条任务的笔记，写完也一直停在「正在写笔记」；现在进度一结束编辑页就去取一次。假模型改成按真实格式回答长录像的提要点、定章节、各章和统一文风，并分几段返回，测试副本上能看到整个过程。
- 实测：测试副本、假模型、一份约 9 万字节的转录稿按章节写，编辑页依次显示提要点、定章节、两章标题、两章正文逐步出现、统一文风、查漏，写完自动换成笔记；处理记录卡片显示「写笔记 · 提要点 0/2」。浅色、深色各看了一遍。Claude 分部分写的显示只有单元测试，没在页面上实测。

### 5.59 他读笔记时说的错漏当场记；点「学完了」时把他的改动留给 agent 改进写法

2026-11-25 · 王愉超同意四步方案（「同意，按四步开做」）；起因是 11-21 产品审查发现笔记反馈一条记录都没有 · Claude 实现，测试副本实测

- 起因：`record_note_feedback` 至今没有一条记录。skill 只在「确认要改写法」那一步要求记，单个错漏不记，工具也没有「这篇没问题」这一种；他读笔记时的改动只进了修改记录，agent 拿不到整理好的对比。他要的是：用产品时的操作也算反馈，学完一个视频能打个标记、收进一处整理好（收进哪里见 6.93）。
- 做法：
  - agent 在他指出错、漏时当场记（`one_off`），他说这篇没问题记 `fine`，不等到要改写法。
  - 点「学完了」（编辑页，或他在对话里说学完了由 agent 调 `mark_studied`）时，FluentFlow 把这篇从最后一次整篇写出以来他的改动整理成一条 `studied` 记录：好用/有错/有漏（可不选）、改了几处、谁改的（网页、Obsidian、飞书拉回、agent 替他改字）、每处的章节和改前改后。没改就点学完，记成「没改过笔记」。只在他点的那一刻整理一次，不是后台盯着他改笔记，和 5.38 不冲突。取消学完会删掉这条记录；再点一次按同一个编号重做，agent 已经记在它名下的结论还对得上。
  - 「最后一次整篇写出的样子」在每次保存笔记时存在过程文件里（`写成时的笔记.md`，之后的改动次数在 `写成后的改动.json`）。原打算从历史版本里找，实测发现网页上的改动要等产出文件夹大约一分钟后同步才留旧版，没有产出文件夹的任务一份都不留，改完马上点学完就看不出改了什么。11-25 以前写成、还没被改过的笔记，第一次改动时把改之前的那版存作写成时的样子；以前改过的，从历史版本里找（两侧都看：从飞书拉回、agent 改字只在 md 那侧留了旧版），截图链接两侧写法不同，先统一成文件名再比，不算改动。
  - agent 读到没处理过的 `studied` 记录（`reviewed=false`）时自己判断每处改动是改正事实、他自己的想法，还是写法问题（由模型判断，不用规则匹配），分别记 `one_off`、`pattern` 并带上 `study_id`；都不是写法问题时记一条 `fine`，这条就算处理过。标了有错或有漏却没改的，问他一次是什么。同一类写法问题记到两次，带两处原文来问他要不要改写法，照 5.38 他点头才改。
- 实测：在真实数据上只读地对 12 条他改过的笔记整理改动，第三课那条原来只看 FluentFlow 一侧时算出 127 处（把 11-14 重写之前的也算进来了），两侧一起看后是重写后 agent 替他改的 6 处（把存疑的词改对）。测试副本上新建任务、网页改两处、置顶、点学完选有错：取消了置顶，记录里两处改动都在，agent 记一条 `fine` 后显示已处理。
- 没做：agent 只在读写法、或他说学完时才看这些记录，没有定时去看；写成时的笔记从这次起才开始存，以前改过又没留旧版的（飞书拉回的两条）记录里写「看不出改了什么」。
