### 8.2 实测方法

2026-10-13 至 14，这两天反复踩的坑

- 测试用复制到临时目录的短片段，不提交他文件夹里的原片：产品会把产物放回原片旁边，一次测试就在他的文件夹里多出一份剪后视频。比编码画质 4 分钟够用，比速度 10 分钟够用，不用跑整段。

### 8.11 实测花钱分三道关：服务设上限、测流程用假模型、测效果先说花费

1. 服务能设一个这次运行的花费上限（调用次数和按 API 价折算的金额），超过就拒绝调用，任务写明超出测试预算。所有调用都经过用量记账那一处，检查只加在那里。
2. 服务有一个假模型开关：每一步按真实格式返回固定内容、不发请求、不花钱。测流程的实测都开它。

### 8.12 实测的花费上限、假模型和测试副本：怎么做的

2026-10-26 · 实现 8.11 · 提交 4191ce7

- 上限和假模型都只在 `model_usage.call` 判断。上限用启动时的环境变量设（调用次数、美元、人民币），按这次运行累计；金额按 API 价算，走订阅的用命令行自己报的 API 价折算，没有价格的只算次数。一种币种的上限只拦按这种币种收钱的服务商：人民币上限用完，Claude 照样能调（实测时设成 0 元，最初的写法把 Claude 也拦了）。花费在调用结束后才知道，最后一次可能超出一点。
- 被拒的调用在请求发出前拦下，记一行失败。很多步骤在模型失败时照常往下走（词表纠错、处理报告、结尾判断），所以「那一步记为失败」不在各步骤里改，而是由 `task_steps.finish` 统一查：这一步有调用因预算被拒，就记为失败、原因写「超出这次测试的模型预算」。
- 假模型由每个出口自己接：`model_usage.call` 把 `call.fake` 设上，出口不发请求，用 `fake_model.reply` 按真实格式造回答（OpenAI 的响应、Anthropic 的消息、命令行的结果事件）。回答按调用所在的细项（`model_usage.item`：判断剪哪里、判断结尾、写正文、查漏……）选格式，细项没写的按提示词要的格式（JSON 数组、JSON 对象、笔记）。笔记是带两个小节的固定文字。查 Claude 登录、查最新的 Claude 模型这两处也不再发请求。用量照记，服务商记成 `fake`，不算钱、不占预算。守护测试查每个 `with model_usage.call(...) as call` 里都有 `if call.fake`。
- 开着任何一个时，`/health` 的 `test_run` 写明，设置页「需要你处理」各写一句、不带按钮（关掉的办法是不带它重启服务）。
- 测试副本由 `scripts/prepare_test_copy.py` 准备，取代手工复制：sqlite 在线备份、关掉副本里没到终点的步骤、关掉副本里的自动导出飞书、默认带预算。副本里的旧任务仍指向真实的笔记文件和飞书文档，所以启动命令另设 `FLUENTFLOW_TEST_COPY=1`，副本服务不监视产出文件夹、不去飞书拉改动。
- 实测（2026-10-26，张和 kickoff 第 600 秒起 4 分钟片段）：假模型一条从提交到每步结束约 2 分 20 秒，5 次调用全是假模型，预算计数 0，剪后视频、笔记 md 和 PDF 都进了产出文件夹。上限设 1 次调用、走 Claude 订阅跑同一片段：词表纠错那 1 次放过（按 API 价折算 0.069 美元），之后判断剪哪里、整理处理报告、写正文 3 次都在发出前被拒，剪辑和写笔记两步记为失败、原因「超出这次测试的模型预算」，没有转去 DeepSeek。


### 8.13 假模型下，订阅那条路启动替身小程序，不直接返回

2026-10-26 · 主对话补的需求 · 提交 6214634

「停下这一步」「关服务时 3 秒内停掉 Claude 命令行」是要实测的流程，假模型直接在程序里返回就测不到。所以假模型打开时，订阅那条路（写笔记、订阅聊天、订阅判断剪辑）照样走 `_run_tracked` 和 `task_stop` 登记，启动的是一个替身小程序（`fake_model.command_line_stand_in`）：读完输入、等 `FLUENTFLOW_FAKE_MODEL_SECONDS` 秒（默认 3）、按命令行的格式打印固定结果。实测（真实数据副本，等待设 20 秒）：写笔记时按停下，替身 0.1 秒内被停掉，剪辑和写笔记记为已停下；接着做之后关服务，替身 0.3 秒内被停掉，写笔记那一步留着没结束，重启后接着做。Key 和文字模型那几条路是 HTTP 请求，停下时本来就只是丢掉回答，仍在程序里直接返回。

### 8.14 测试副本上的服务只能动副本里新建的任务

2026-10-26 · 主对话验收时提出 · 提交 3b139e2

验收查出：副本里的任务仍指向真实的东西（原片旁边的产出文件夹、飞书文档、真实数据目录里的产物），只关步骤不够。副本里还在排队或进行中的任务，启动时会用原片新建一条从头重跑；笔记一保存就同步的两个监听也不看开关。所以在测试副本上（`FLUENTFLOW_TEST_COPY`，判断都在 `backend/core/test_copy.py`）：

- 脚本把副本里所有任务的编号写进 `test_copy_tasks.json`，这些旧任务只能看：服务对每个请求查一次，地址或请求里点名了旧任务的写请求一律拒绝（409，「这是测试副本里的旧任务，只能看。」），网页和 agent 走同一处；导出到飞书整个拒绝。只在请求里给笔记路径的复习笔记，在写之前另查一次。
- 产出文件夹的同步对旧任务直接不做；飞书推送、拉回、「笔记一保存就推」都不做；发飞书这一步跳过；原片副本到期也不清理。产出文件夹那一处没有像飞书那样整个关掉：副本里新提交的任务要照常把笔记放进新片段旁边的文件夹，实测要看这个。
- 开着时 `/health` 和设置页写明。`models` 软链不改：服务只读它（转录模型在 Hugging Face 的缓存，说话人模型只由安装脚本下载）。
- 金额上限按已经花的放行，几次同时在跑的调用都会放过，最多超出「同时在跑的调用数 × 一次的费用」，维护手册照实写，不做预留。假模型开着时，检查 Key、列模型、读推荐模型表这几个不花钱的请求也不发。
- 脚本默认的预算 40 次、1 美元、1 元保留（主对话验收时同意）。
- 实测（真实任务库副本，136 条旧任务，另放两条人为的进行中、排队中任务）：启动后任务数不变、什么都没排队，两条都在副本里记为失败；对一条旧任务重写笔记、删除都回 409；新提交的 4 分钟片段每步做完，剪后视频、笔记 md 和 PDF 进了新片段旁边的文件夹。

### 8.27 Windows 上一直失败的测试：查清原因再修，一条用户真会碰到

2026-11-25 · 王愉超定开工（发 0.11.0 前的 Windows 检查留下 6 条失败）

- 先在 GitHub 的 Windows 机器上重跑：串行跑仍是那 6 条；四路并行跑多出同一个文件里的 3 条，同一个原因。逐条查清后分两类，都没有用跳过来变绿。
- 用户真会碰到的（修了产品代码）：一条任务开始处理时，要把它的七个步骤写进任务库，原来每个步骤单独提交一次。每次提交都要等磁盘写完，在 GitHub 的 Windows 机器上量到中位 33 毫秒、最慢 400 毫秒（Mac 上不到 1 毫秒），而且这一步在服务回答网页和 agent 的同一个线程上做，于是在 Windows 上每开始一条任务，整个服务就卡住几百毫秒到一两秒，网页和 agent 的请求都等着。改成一次提交写完（`job_store.write_task_steps`，接着做时重开后面步骤也一样），`tests/test_task_steps.py` 数着打开任务库的次数守着。真人 Windows 电脑上的磁盘多半比 GitHub 的机器快，卡顿会短些，没在实机上量过。别处也有在这个线程上写任务库的（开始、结束某一步各一次），每次只一笔，这次没动。
- 测试本身在 Windows 上写得不对的（只改测试）：
  - 随看笔记只读用户目录：测试只改了 `HOME`，Windows 上 Python 认的用户目录是 `USERPROFILE`，而测试的临时目录本来就在真实用户目录里，「目录外的笔记」于是也在目录内。测试同时设 `USERPROFILE`。产品在 Windows 上按 `USERPROFILE` 判断，是对的。
  - 假模型三条：测试把一切网络连接都当成「发出了真实请求」，可 Windows 上 Python 每建一个事件循环，都会在本机 127.0.0.1 上自己连自己一次（用来唤醒循环），不出这台电脑。测试放过这一种连接，别的照拦。
  - 排队的四条：测试固定等半秒、或最多等两秒、门闸五秒自动打开；Windows 上任务库写得慢，到点时状态还没到，门闸自己开了还会让笔记像被放行一样往下走。改成等到状态出现为止（最多 10 秒），门闸 30 秒。
- 开发自用工具（不影响用户）：测试副本工具在 Windows 上打印的是 Mac 的启动命令（`.venv/bin/python`、`&&`、POSIX 引号），默认数据目录也写死成 Mac 的。改成 Windows 上打印 PowerShell 命令，默认数据目录用 `runtime_paths.app_data_root()`。副本里的 `models` 仍是软链，Windows 上普通用户建软链要开发者模式，没人在 Windows 上开发，这次不改。
- 结果：GitHub 的 Windows 机器上全套测试全过，Mac 上全过。
