# Independent Local Repository

FluentFlow Local is maintained here as an independent source repository. It has its own local application entrypoint, frontend build, tests, CI, launchers, dependencies and release history.

`docs/05-仓库边界.md` is the mandatory entry point for new conversations
and cross-repository work. It overrides any historical wording that describes
this repository as a generated export.

The hosted FluentFlow repository may retain similar implementations where each product needs them, but neither repository is a generated mirror of the other. Changes required by both editions are intentionally ported and reviewed in each repository; do not create a new shared-base repository merely to remove duplication.

The local app keeps existing user data compatibility through `backend/core/runtime_paths.py`. Repository maintenance must not delete or relocate the system application-data directory, local credentials, task history, media, or generated results.

For normal development, install `requirements-local.txt`, then run `npm run build:frontend` and start `backend.local_main:app`. CI validates the local frontend and the selected local backend suite on Python 3.10.

看界面改动不用重启 8000 上的服务：在工作副本里跑 `npx vite --config vite.local.config.mjs --host 127.0.0.1 --port 4173 --strictPort`，从 `http://localhost:4173/local.html` 打开。4173、5173、5186 这几个开发端口的页面会把请求发到 `127.0.0.1:8000`（`frontend/src/lib/apiBase.js`），看到的是真实任务，所以只看、不点删除和重新提交这类会改数据的按钮。几个对话同时改界面时各用一个端口，5186 常被别的对话占着。2026-10-22 界面走查线一实测可用。要放心点按钮、截图，用只读预览：`npx vite --config vite.preview-records.config.mjs --host 127.0.0.1`，从 `http://localhost:5197/<页面>` 打开，它把读请求转给 8000，所有写请求一律拒绝（2026-10-23 处理记录页重做实测，同日统一视觉一轮修好后再测过）。截三档宽度的图可以用无头 Chrome：`"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --hide-scrollbars --window-size=1024,900 --virtual-time-budget=10000 --screenshot=<文件> <网址>`。暗色模式由浏览器本地存储里 `fluentflow_settings` 的 `theme: "dark"` 决定，命令行截图设不了；要截暗色，用 Playwright 驱动本机 Chrome 在页面加载前写入这一项，或在桌面 App 的内置浏览器里打开页面、用脚本写入这一项再刷新（2026-10-25 第二批截图实测）。

yt-dlp（抖音、B 站、YouTube 的下载器）不进任何锁定文件：安装脚本在装完锁定依赖后单独装最新版，macOS 和 Windows 启动器每次启动时在后台运行 `scripts/update_yt_dlp.py`，每天最多升级一次（成功的日期记在数据目录的 `yt_dlp_last_update`，失败不记、下次启动再试），升级后的下一次链接下载就用新版本。要立刻更新，运行 `.venv/bin/python scripts/update_yt_dlp.py --force`（Windows 为 `.venv\Scripts\python.exe scripts\update_yt_dlp.py --force`）；国内网络先设 `PIP_INDEX_URL` 镜像。

## 各家文字模型的默认：推荐模型表

各家文字模型的默认写在 `backend/core/recommended_models.json`：每家写「够用里最便宜的一档」，有「始终指向最新」的名字就用那个名字（如 `deepseek-flash`、`qwen-plus`）。FluentFlow 每天在后台读一次 GitHub main 上的这个文件，读到能用的就存一份在数据目录里，下次直接用；读不到就用存下的那份或自带的那份。所以**改默认模型只改这个文件、推到 main，用户不用升级**。

什么时候改：发版前，或者听说哪家出了新模型、停了旧名字时，查一次各家官方的模型和价格页（DeepSeek：api-docs.deepseek.com 的 Models & Pricing 和 Change Log；OpenAI：developers.openai.com 的 Models 和 Deprecations；通义千问：百炼的模型列表和模型下线页）。查文档就够，不必每次花钱实测。服务商停用某个名字后，调用时也会自动换成这家现在的默认（`ai_client._create`），所以这张表是为了用上更好的模型，不是为了不出错。

用户在设置页没选过模型时，存的是「跟随默认」，表一改就跟着换；自己选过的才固定用他选的。

## 模型用量和价格表

每次调用模型（DeepSeek 这类文字模型、设置里的看图模型、Anthropic Key、Claude 订阅命令行，连设置页检查 Anthropic Key 的那一次也算）在任务库的 `model_calls` 表里记一行：任务、步骤、步骤里的哪一项、服务商、模型、付费方式（`key` / `subscription`）、输入 token、其中命中缓存的、写进缓存的、输出 token、耗时、成没成功、时间（UTC）。记录写在调模型的出口里（`backend/core/model_usage.py` 的 `call`），归到哪个任务哪一步靠上下文带过去；`step` 为空的就是「没归到步骤」，处理过程页和 agent 都能看到；`task_id` 为空的（检查 Key、整理笔记风格、线程丢了任务的）在设置页「账号和 Key」最下面一行和 agent 的 `get_status` 里。查一条任务：`sqlite3 <数据目录>/fluentflow_jobs.sqlite "select step, item, provider, model, input_tokens, cached_input_tokens, output_tokens, ok from model_calls where task_id='<任务>'"`。

钱数不存，显示时按 `backend/core/model_prices.json` 算：每家写官方定价页的网址、核实日期和收钱的币种（DeepSeek 用中文定价页的人民币价，国内平台按它扣费；英文页的美元价是另一套），每档价格写适用的模型名和生效时间（`from`，带时区，写北京时间零点），DeepSeek 另写高峰时段（换算成 UTC）。改价格：到官方页核实，加一档新价、`from` 写新价生效那天，旧的留着给之前的调用用；只填官方页上核实过的模型，没有价格的只显示 token。价格表随版本发出，故意不放进每天从 main 读的推荐模型表（决策 6.41、6.44）。DeepSeek 的法定节假日按非高峰收费，表里没有节假日日历，节假日工作时段的调用按高峰价算，最多高估一倍。

## 在真实数据的副本上实测

用真实任务库的副本在别的端口起完整服务实测，用 `scripts/prepare_test_copy.py` 准备副本，不手工复制（决策 8.11）：

```bash
.venv/bin/python scripts/prepare_test_copy.py --into <scratchpad 里的目录> --fake --port 8013
```

它用 sqlite 的在线备份复制任务库和事件库（8000 上的服务照常跑），复制 `fluentflow_config.json`（副本里关掉自动导出飞书）和 `recommended_models.json`，`models` 用软链；再把副本里没到终点的步骤关掉（记为跳过）、还在排队或进行中的任务记为失败（原因 `test_copy_unfinished`）：不关的话，启动时会把这些任务从中断的那一步接着做，或者用原片新建一条从头重跑，8000 上正在跑的任务会在副本里再跑一遍，花一次钱，还会往原片旁边的产出文件夹里写（2026-10-26 撞上过一次）。最后把副本里所有任务的编号写进 `test_copy_tasks.json`。只读原数据目录，只写副本；副本目录不能放在原数据目录里面。最后打印启动命令，从这个检出目录起服务；要在这个服务上看页面，先在这个检出目录构建前端（`npm run build:frontend`）再起服务，否则页面是空白的。

启动命令默认带这次运行的模型预算（最多 40 次调用、1 美元、1 元，用 `--max-calls`、`--max-usd`、`--max-cny` 改，`--no-limit` 去掉，去掉要王愉超点头），并设 `FLUENTFLOW_TEST_COPY=1`。副本里的旧任务仍指向他真实的东西：原片旁边的产出文件夹和里面的笔记、飞书文档、真实数据目录里的产物（多数任务的结果用绝对路径记着）。所以这样起的服务（`backend/core/test_copy.py`）：

- 启动时不接着做、不重排任何任务，副本里没到终点的步骤和任务在副本里关掉；
- `test_copy_tasks.json` 里的旧任务只能看：对它们的写请求（重剪、重写笔记、恢复版本、删除、在它旁边写复习笔记）一律拒绝，回「这是测试副本里的旧任务，只能看。」，网页和 agent 一样；在副本里新提交的任务照常处理，产出写在新片段旁边；
- 不写旧任务的产出文件夹，不往飞书推、不从飞书拉、不导出到飞书，不监视产出文件夹里笔记的改动，不清理到期的原片副本；
- `/health` 的 `test_run.test_copy` 为真，设置页「需要你处理」写一句。

`models` 是软链，副本服务只读它：转录模型下到 Hugging Face 自己的缓存目录，说话人模型只由安装脚本下载，服务不往这个目录写。

- **测流程**（重启、停下、接着做、导出这类不看模型写了什么的）加 `--fake`，开假模型：每个调用模型的出口按真实格式返回固定内容，不发请求，不启动 `claude` 命令行。走 Claude 订阅的那条路（写笔记、订阅聊天、订阅判断剪辑）改为启动一个替身小程序：读完输入，等几秒（`FLUENTFLOW_FAKE_MODEL_SECONDS`，默认 3 秒），按命令行的格式打印固定结果后退出。它和真的命令行一样登记、一样被停掉，所以「停下这一步」「关服务时停掉命令行」照样能测：要来得及按停下，把等待设长一点，比如 20 秒。剪辑保留按音量找出的停顿，照样导出剪后视频；结尾不裁；转录稿一句不改；笔记是一段固定文字，带两个小节，能存、能放进产出文件夹、能导出 PDF；查漏都算写到了。用量照记，服务商记成 `fake`，不算钱，也不占预算。
- **测模型效果**不加 `--fake`，带着预算跑。超出预算时，`model_usage.call` 在请求发出前拒绝，记一行失败的调用（原因「超出这次测试的模型预算」），那一步结束时记为失败、写同一个原因，哪怕这一步本来会在模型失败时照常往下走（`task_steps.finish`）。金额按 API 价算，走订阅的调用用命令行自己报的 API 价折算，没有价格的模型只算次数；一种币种的上限只拦按这种币种收钱的服务商。花费在调用结束后才知道，放行时只看已经花了的：同时在跑的几次调用都会被放行，所以金额最多会超出「同时在跑的调用数 × 一次的费用」（一条任务里修正转录稿、剪辑、写笔记会同时调用）。次数上限不会超。

开着假模型时，设置页那几个不花钱的请求也不发：检查 DeepSeek、通义千问等的 Key（直接答「假模型开着，没有真的检查这个 Key」），列服务商的模型，每天读一次 main 上的推荐模型表。

开着假模型或预算时，`/health` 的 `test_run` 写明（`fake_model`、`budget`、`spent`），设置页最上面「需要你处理」各写一句。往 Agent 接口提交任务要带 `.env` 里的 `FLUENTFLOW_ACCESS_TOKEN`（`Authorization: Bearer …`），本机路径提交是 `POST /agent/v1/tasks`，`{"path": …, "input_type": "local_path"}`。

## 环境变量

后端和脚本读取的每个 `FLUENTFLOW_*` 变量。写进仓库根目录 `.env` 或启动时的 shell 环境都行；没列默认值的，不设就是关闭或不覆盖。来源按 `backend/` 与 `scripts/` 里的 `os.environ` 读取处整理，改了读取处要同步这里。

### 服务与数据位置

| 变量 | 含义 | 默认 |
| --- | --- | --- |
| `FLUENTFLOW_LOCAL_HOST` | 监听地址 | `127.0.0.1` |
| `FLUENTFLOW_LOCAL_PORT` | 监听端口；macOS 启动器也读这一项 | `8000` |
| `FLUENTFLOW_ALLOW_NON_LOOPBACK` | 为真时接受局域网请求，否则只收本机；其他设备除页面本身外每个请求都要带 `FLUENTFLOW_ACCESS_TOKEN` | 关 |
| `FLUENTFLOW_ALLOWED_HOSTS` | 除 127.0.0.1、localhost、[::1]（局域网模式再加 IP 和本机 `.local` 名）之外，服务还回应哪些 `Host`，逗号分隔；服务前面有反向代理时填代理用的名字 | 空 |
| `FLUENTFLOW_DATA_DIR` | 运行数据根目录 | 系统应用数据目录，macOS 为 `~/Library/Application Support/FluentFlow` |
| `FLUENTFLOW_CONFIG_PATH` | 设置页写入的凭据与偏好文件。偏好里的 `ai_provider`、`ai_model`、`speaker_diarization`、`export_to_lark` 是任务没指定时用的写笔记模型、区分讲话人和自动导出（决策 6.31），网页和 agent 的任务都读它；存的服务商没有 Key 时退回第一家有 Key 的，`GET /preferences` 的 `text_model` 给出实际会用哪家 | `<数据目录>/fluentflow_config.json` |
| `FLUENTFLOW_JOB_DB_PATH` | 任务数据库 | `<数据目录>/fluentflow_jobs.sqlite` |
| `FLUENTFLOW_EVENT_DB_PATH` | 事件数据库 | `<数据目录>/fluentflow_events.sqlite` |
| `FLUENTFLOW_SOURCE_DIR` | 网页上传、链接以外的原片副本（从本机选的文件原地读取，不在这里） | `<数据目录>/sources` |
| `FLUENTFLOW_ARTIFACT_DIR` | 转录、笔记、剪辑产物 | `<数据目录>/artifacts` |
| `FLUENTFLOW_EDITED_TRANSCRIPT_DIR` | 手动改过的转录稿 | `<数据目录>/edited_transcripts` |
| `FLUENTFLOW_TRANSCRIPT_EDIT_RECORDS_DIR` | 转录稿修改记录 | `<数据目录>/transcript_edit_records` |
| `FLUENTFLOW_VIDEO_SOURCE_DIR` | 从链接下载的视频 | `<数据目录>/video_sources` |
| `FLUENTFLOW_SPEAKER_BACKEND` | 讲话人区分用哪套程序：`sherpa` 是随应用装好的默认；`pyannote` 更准、更慢，要另装约 900MB（`requirements-speaker.txt`，再运行 `scripts/fetch_pyannote_models.py`）。选了 `pyannote` 但没装好时，自动改用 `sherpa`，任务结果里写明原因 | `sherpa` |
| `FLUENTFLOW_DIARIZATION_MODEL_DIR` | 默认讲话人区分（sherpa-onnx）的模型目录，放 `segmentation.onnx` 和 `embedding.onnx`，由 `scripts/fetch_diarization_models.py` 填充，安装脚本会自动运行它 | `<数据目录>/models/speaker` |
| `FLUENTFLOW_PYANNOTE_MODEL_DIR` | 可选的 pyannote 讲话人区分的模型目录，由 `scripts/fetch_pyannote_models.py` 填充 | `<数据目录>/models/pyannote` |
| `FLUENTFLOW_SOURCE_RETENTION_DAYS` | FluentFlow 另存的原片保留多少天，`0` 为一直保留。设为正数才会清理：上传文件的副本到期删除；从链接下载的视频只有在已有去气口版本时才到期删除。任务产出的其他东西都不会被自动删除 | `0` |

### 限额与超时

| 变量 | 含义 | 默认 |
| --- | --- | --- |
| `FLUENTFLOW_MAX_UPLOAD_MB` | 网页上传单个文件的上限（MB），设了才限制；从本机选的文件和视频链接不受它限制（链接要设上限用 `VIDEO_SOURCE_MAX_BYTES`，单位字节；不设时只在磁盘空间不够时拒绝） | 不限 |
| `FLUENTFLOW_MAX_TRANSCRIPT_UPLOAD_MB` | 单个转录稿文件上限 | `64` |
| `FLUENTFLOW_MAX_QUEUE_FILES` | 网页一次上传的文件数上限，和从本机选文件、选文件夹的 30 个一致 | `30` |
| `FLUENTFLOW_MAX_MEDIA_DURATION_SECONDS` | 媒体时长上限（秒），设了才限制 | 不限 |
| `FLUENTFLOW_MAX_TRANSCRIPT_EDIT_CHARS` | 编辑转录稿时的字数上限 | `1000000` |
| `FLUENTFLOW_MAX_SUMMARY_EDIT_CHARS` | 编辑笔记时的字数上限 | `500000` |
| `FLUENTFLOW_STALE_JOB_SECONDS` | 转录多久没有任何进展算卡住、中止它；只看有没有进展，不限总时长 | `7200` |
| `FLUENTFLOW_FILE_CHOOSER_TIMEOUT` | 系统文件选择框等待秒数 | `300` |
| `FLUENTFLOW_YT_DLP_DOWNLOAD_TIMEOUT_SECONDS` | 固定的链接下载超时；不设则按视频时长估算 | 按时长估算 |
| `FLUENTFLOW_YT_DLP_MAX_TIMEOUT_SECONDS` | 估算出的下载超时的上限（估算按视频时长和大小增长） | `21600` |

### 处理流程开关

开关类变量用 `1/true/yes/on` 打开、`0/false/no/off` 关闭。

| 变量 | 含义 | 默认 |
| --- | --- | --- |
| `FLUENTFLOW_CAPTIONS_FIRST` | YouTube、B 站链接有字幕时只取字幕、不下载视频（快，但没有画面、没法剪、不留原片） | 关 |
| `FLUENTFLOW_LINK_OUTPUT_DIR` | 链接下载的视频连同处理结果放在哪个文件夹下，每个视频一个子文件夹 | macOS `~/Movies/FluentFlow`，Windows 和 Linux `~/Videos/FluentFlow` |
| `FLUENTFLOW_NORMALIZE_UNEVEN_RATE` | 帧率不均匀的录像先整条转成固定帧率再剪（多编码一遍；默认直接剪，每段剪的时候已统一帧率） | 关 |
| `FLUENTFLOW_MODEL_TABLE_URL` | 推荐模型表从哪里读；设为空则不联网读，只用自带的那份 | GitHub main 上的 `backend/core/recommended_models.json` |

文本笔记的默认提示词是 `backend/core/ai_prompts.py` 里的常量 `FLUENTFLOW_SYSTEM_PROMPT`，不从环境变量读；要换提示词，在设置页或提交时传 `system_prompt`。

笔记的历史版本在 md 旁边的「过程文件/历史版本」，文件名 `<md 名>_<本地|FluentFlow|飞书>_<时间>_<谁换掉的>.md`；没有产出文件夹的任务存在数据目录 `artifacts/<任务号>/过程文件/历史版本`。「谁换掉的」来自改写笔记的那个入口在结果里写下的 `note_changed_by`（`backend/core/note_versions.py` 的 `declare`），带着它写下的笔记的指纹，指纹对不上就记「未记录」。新加一个会改写任务笔记的入口时，写入前调用 `declare`，并在 `tests/test_note_history.py` 加一条；某个版本显示「未记录」而它是新存的，就是有入口漏了声明。每次修改改了什么写在旁边的「过程文件/修改记录.md」（`backend/core/note_changes.py`）：它挂在 `job_store` 的结果监听上，只看任务自己的笔记 `summary_markdown` 前后两版，所以 md 和飞书那份随后被覆盖不会再记一条；写失败只记日志。这个监听在保存的线程里同步跑，超过 `LONGEST_COMPARED`（3000 字）的段落只比首尾，别为了摘得更准改回逐字比：单段 2 万字逐字比要 1.5 到 1.9 秒。飞书那一侧的旧版只在飞书里被改过时才存：推送前把飞书现在的样子按章节整理后的指纹（`feishu_note.feishu_section_records`）和上次推送后记下的 `sync.pushed_sections` 比，一样且笔记有产出文件夹就不存（2026-10-23 前同步、之后还没再推过的笔记没有这一项，一律当作飞书改过、存一份：拉回会改写 `feishu_sections`，拿它比会漏掉拉回过的飞书修改；推一次之后就有这一项了）。agent 用 MCP 的 `list_note_versions`、`read_note_version`、`restore_note_version`（`/agent/v1/tasks/{id}/note/versions…`，`backend/core/note_history.py`）列出、读取、恢复；恢复走网页编辑保存的同一套字段，带列出时的 `note_version`，对不上返回 409 `stale`；核对和写入是同一次数据库写（`job_store.save_result_changes` 的 `unless_moved`），别的写入要「只在某个字段没变时才写」也用它。agent 的笔记写入（存笔记、重写、恢复上一版、切回生成版）带 `base_version` 时用同一函数的 `expect_versions`，在写入那一次核对笔记版本，对不上抛 `VersionMoved`，接口回 409 `stale`（决策 6.30）；agent 读到的版本在 `get_task`、`get_task_package`、`get_agent_note_material` 的 `note_version` 里。

复习笔记（决策 5.37）的写法在 `backend/note_skills/fluentflow-review-note/SKILL.md`，生成和修改在 `backend/core/review_note.py`，agent 走 `POST /agent/v1/review-notes`（MCP `write_review_note`）和 `/review-notes/revise`（`revise_review_note`），同步执行，三小时的访谈一次约 8 到 10 分钟。底稿是磁盘上的随看笔记 md，不是任务里存的那份；任务按产出文件夹里的 `output_folder.md_path` 找，文件夹挪走了由 agent 传 `note_path`，再按那个文件夹里的 `.fluentflow-task` 找回任务。出处的时间取任务的 `note_section_times`（跟随播放的章节对照），没有就只给模型转录稿；转录稿先用任务的 `display_segments`，没有任务时用「过程文件」里的 srt。模型只写〔S12 1:05:20〕这样的章节编号，程序换成 Obsidian 链接 `[[<随看笔记名>#章#节|第几章（几）]]`，修改时再换回编号交给模型，链接不会被抄错。模型先用订阅，运行中失败换用户的 Anthropic Key（`max_tokens` 64000，默认的 16000 写不完一篇），再没有用文字模型的 Key；回答缺「主线」「术语表」「自测题」「还没弄清的」「出处信息」任一节就当作没写完，不写入。底稿是哪一版（修改时间、sha256 前 12 位）由程序写在「出处信息」最后一行，任务结果的 `review_note` 也记一份；重新生成或修改前，旧的一份存进「过程文件/历史版本」（没有就建），新的一份先写到旁边的临时文件再换上，PDF 也先印到临时文件，印不出来如实报、不拿旧的那份充数。底稿路径先解析成真实位置，必须在用户主目录下，文件名是 `<名>_笔记.md` 或 `<名>_笔记 (2).md`，或在带 `.fluentflow-task` 的文件夹里；任务按标记里每行的后缀对上文件名找（同一文件夹里第二条任务的文件带「 (2)」），复习笔记照同样的规则叫 `<名>_复习笔记 (2).md`。标题里有 `[ ] | # ^` 这类 Obsidian 跳不过去的字符时，出处只写「第几章 时间」不写链接；修改时换不回编号的旧链接用〔L1〕占位、原样放回；写错格式或编出来的编号写成「（出处待核）」并在回复的 `unknown_sources` 里列出。

推送到飞书后要读一次飞书的章节目录，记下每章标题块的 id（`sync.sections`），下次只改变了的章。这一步失败时 `sections` 记为空、任务上写 `lark_sync_error`，这篇仍算在同步（`lark_cli_exporter.sections_unread`）；下次推送或拉回前 `reread_sections` 用上次推送的笔记（数据目录 `artifacts/<任务号>/feishu_pushed.md`）对上飞书现在的目录重建，读不到就不写（决策 6.38）。

## 事件记录

每个任务的关键步骤写进本机事件库 `fluentflow_events.sqlite` 的 `events` 表（路径见 `backend/core/runtime_paths.py`）。这里只记时间、数量和失败原因，不存转写稿或笔记的正文；任务被保留策略删除后，它的事件仍然留着，所以分析历史用事件库，不用任务库。

下面这些事件回答「时间花在哪」和「为什么没有笔记」：

| 事件 | 什么时候记 | 回答的问题 |
| --- | --- | --- |
| `queue_wait_completed` | 任务排在别的任务后面、轮到它时 | 排队等了多久、排在谁后面。`task_completed` 的总时长从提交算起，包含这段等待 |
| `debreath_completed` / `debreath_failed` | 转写前自动去气口、或手动去气口结束时 | 用时、剪掉多少、阈值是否按素材调整、剪后文件有没有被用来转写；`outcome` 说明没用的原因 |
| `summary_skipped` | 流水线不写自己的笔记时 | `reason` 区分「用户只要转写稿」和「笔记稍后结合画面来写」 |
| `visual_note_unavailable` | 自动笔记开着、但结合画面的笔记写不了时 | 为什么写不了（例如没有或填错 Anthropic API Key；选用订阅通道时还可能是 Claude 登录过期），这个任务改用文本模型写笔记 |
| `visual_note_completed` / `visual_note_failed` | 结合画面的笔记写完或失败时 | 总用时、其中挑截图的本机用时、用了多少张截图、失败原因；`trigger` 区分自动和手动 |
| `task_interrupted_by_restart` | 服务启动时处理被上一次重启打断的任务 | 哪些任务被打断、从哪一步接着做（`resumed_from_step`），或为什么留给用户 |
| `task_step_stopped` | 用户或 agent 停下一个任务正在做的那一步 | 停的是哪一步、杀掉了几个它启动的进程 |
| `task_resumed` | 用户或 agent 让一个任务接着做 | 从哪一步接着做 |

`stt_completed` 里的 `model_load_seconds` 只算加载模型本身；Apple 芯片上转写第一段的时间另记在转写日志里。每次转写都在自己的进程里跑，这样取消时能干净地停下来；代价是每个任务都要重新加载一次模型，多花几秒（2026-10-08 实测 large-v3 MLX 为 1.6 到 2.5 秒），权衡后不值得为此常驻一个转写进程。
